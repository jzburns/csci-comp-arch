\begin{frame}{What is Computer Architecture?}

\key{Computer Architecture}
defines the
\key{externally visible capabilities and behavior}
of the machine---the \key{what}.

\vspace{0.2em}

\begin{itemize}
  \item The programmer-visible specification
        of the computer system.
  \item Establishes what software may request
        and what architectural state changes occur.
  \item Provides the stable target
        used by compilers,
        operating systems,
        and assembly programmers.
\end{itemize}

\vspace{0.25em}

\begin{block}{Architectural Specifications Include}

\begin{itemize}
  \item The \key{ISA}:
        instruction encodings,
        operations,
        and semantics.
  \item Programmer-visible state:
        registers,
        stack pointer,
        program counter state,
        and status information.
  \item Data types,
        addressing behavior,
        memory model,
        and exception behavior.
\end{itemize}

\end{block}

\end{frame}

% ============================================================
% Slide 10
% ============================================================

\begin{frame}{What is Computer Organization?}

\key{Computer Organization}
describes the
\key{internal hardware implementation}
of the architecture---the \key{how}.

\vspace{0.2em}

\begin{itemize}
  \item The arrangement of operational units
        and their interconnections.
  \item Defines how the machine physically realizes
        each architectural operation.
  \item Internal details are generally
        \key{not part of the programmer-visible
        architectural contract}.
\end{itemize}

\vspace{0.25em}

\begin{block}{Organizational Structures Include}

\begin{itemize}
  \item Datapaths,
        control units,
        ALUs,
        register files,
        and multiplexer routing.
  \item Pipeline organization,
        branch prediction,
        and cache hierarchies.
  \item Internal interconnects,
        clocking,
        memory controllers,
        and implementation-specific timing.
\end{itemize}

\end{block}

\end{frame}

\begin{frame}{Architectural Stability and Hardware Evolution}

\small

\begin{block}{Why a Stable Architecture Matters}
A stable ISA allows software
to retain the same machine-level meaning
while processor implementations evolve
for performance,
power,
and cost.
\end{block}

\vspace{0.12cm}

\begin{columns}[T,onlytextwidth]

\column{0.48\textwidth}

\begin{block}{Architectural Stability}

\begin{itemize}
  \item AArch64 defines instructions
        such as
        \code{add},
        \code{ldr},
        and \code{cbz}.
  \item Their architectural meaning
        remains stable
        across compliant implementations.
  \item Binary compatibility also depends on
        the operating environment,
        ABI,
        and supported extensions.
\end{itemize}

\end{block}

\column{0.48\textwidth}

\begin{block}{Organizational Evolution}

\begin{itemize}
  \item One core may use
        a modest in-order pipeline.
  \item Another may use
        wide out-of-order execution
        and larger cache hierarchies.
  \item Both can preserve
        the same architectural
        instruction semantics.
\end{itemize}

\end{block}

\end{columns}

\end{frame}

\begin{frame}{The Instruction Set Architecture (ISA)}

The \key{ISA}
defines the processor interface
visible to machine-language software.

\begin{itemize}
  \item Instructions and their semantics.
  \item Programmer-visible registers
        and status state.
  \item Instruction encodings
        and operand forms.
  \item Memory-access
        and exception behavior
        exposed to software.
\end{itemize}

\vspace{0.25cm}

\begin{block}{Architectural Contract: \code{add x1, x2, x3}}

The ISA guarantees the architectural state change:

\[
\code{x1}
\leftarrow
\code{x2}
+
\code{x3}
\]

It defines \textit{what}
result must become visible,
not the internal wiring
or timing used to produce it.

\end{block}

\end{frame}

% ============================================================
% Slide 15
% ============================================================

\begin{frame}{One Possible Microarchitecture for \code{add x1, x2, x3}}

\begin{block}{Illustrative Register-Transfer Steps}

\begin{enumerate}
  \item Present \code{x2} and \code{x3}
        as register-file read addresses.
  \item Read the two 64-bit operand values
        from the register file.
  \item Configure the ALU
        to perform addition.
  \item Compute:
        \code{alu\_result <- x2 + x3}.
  \item Enable a write
        to destination register \code{x1}.
  \item Commit the result
        to the architectural register file.
\end{enumerate}

\end{block}

\vspace{0.15cm}

\begin{itemize}
  \item \key{ISA view}:
        required state change.
  \item \key{Microarchitecture view}:
        control signals,
        data movement,
        and execution resources.
  \item Signal names here are teaching abstractions,
        not AArch64 architectural state.
\end{itemize}

\end{frame}

\begin{frame}{The Stored-Program Concept}

\begin{block}{Stored-Program Definition}
Program instructions are represented
as binary information
and stored in memory,
allowing the computer
to execute different programs
without changing the hardware.
\end{block}

\vspace{0.12cm}

\begin{itemize}
  \item The processor stores and retrieves
        program information
        and runtime data electronically.
  \item A program counter identifies
        the next instruction to be fetched.
  \item Reprogramming means loading
        a different instruction sequence
        rather than rewiring the machine.
  \item The stored-program idea does
        \key{not} require instruction
        and data accesses
        to use the same physical memory path.
\end{itemize}

\vspace{0.05cm}

\begin{block}{Memory Organization Is a Separate Choice}
Von Neumann and Harvard
are different ways
to organize instruction
and data access
in a stored-program computer.
\end{block}

\end{frame}

\begin{frame}{Memory as an Addressable Array}

\begin{columns}[T,onlytextwidth]

\column{0.56\textwidth}

\begin{itemize}
  \item Memory is viewed logically
        as a sequence
        of storage locations.
  \item AArch64 systems are typically
        \key{byte-addressed}:
        each address identifies one byte.
  \item Larger values span
        consecutive byte addresses.
  \item The address identifies
        \textit{where};
        the stored bits
        are the \textit{payload}.
\end{itemize}

\vspace{0.05cm}

\begin{block}{Example}
A 32-bit value beginning
at \hex{1000}
occupies addresses
\hex{1000}--\hex{1003}.
\end{block}

\begin{frame}{Shared versus Separate Memory Paths}

\begin{block}{What Changes?}
Instruction access
and data access
either share one memory path
or use separate paths.
\end{block}

\vspace{0.35cm}

\begin{columns}[T,onlytextwidth]

\column{0.48\textwidth}

\begin{block}{Shared Path: von Neumann}

\begin{itemize}
  \item Instruction fetch
        and data access
        can compete for
        the same resource.
  \item Simpler memory organization
        and flexible sharing
        of storage capacity.
\end{itemize}

\end{block}

\column{0.48\textwidth}

\begin{block}{Separate Paths: Harvard}

\begin{itemize}
  \item Removes instruction/data
        memory-path contention.
  \item Requires separate storage interfaces
        and additional hardware resources.
\end{itemize}

\end{block}

\end{columns}

\vspace{0.25cm}

Neither organization
eliminates all processor stalls;
the distinction concerns
the structure of instruction
and data access.

\end{frame}

\begin{frame}{Topic Summary}

\begin{itemize}
  \item \key{Architecture vs. Organization}:
        architecture defines
        software-visible behavior;
        organization implements it
        in hardware.
  \item \key{ISA vs. Microarchitecture}:
        the ISA specifies instructions
        and architectural state;
        microarchitecture realizes
        those semantics
        with datapaths and control.
  \item \key{Stored-Program Concept}:
        instructions are represented
        as binary information
        stored in memory,
        allowing programs to change
        without rewiring hardware.
  \item \key{von Neumann}:
        instruction and data accesses
        share memory resources.
  \item \key{Harvard}:
        instruction and data accesses
        use separate memories and paths.
  \item \key{Modified Harvard}:
        separate instruction/data structures
        near the core
        with a unified lower memory system.
\end{itemize}

\end{frame}

\begin{frame}{Self-Test: Solutions 1--3}

\vspace{-0.08cm}

\begin{block}{Solution 1}
\key{Architecture}:
software-visible specification,
such as instruction semantics
and visible registers.

\key{Organization}:
internal implementation,
such as pipeline structure
and cache organization.
\end{block}

\begin{block}{Solution 2}
\key{ISA}:
add the values in
\code{x2} and \code{x3}
and place the result
in \code{x1}.

\key{Microarchitecture}:
read operands,
control the ALU,
move the result,
and write the destination register.
\end{block}

\begin{block}{Solution 3}
Instructions are stored
as binary information in memory.

Loading a different instruction sequence
changes the program
without changing the physical hardware.
\end{block}

\end{frame}

\begin{frame}{Self-Test: Questions 4--5}

\begin{block}{Question 4: von Neumann vs. Harvard}
What is the primary structural difference
between von Neumann
and Harvard organizations?

Why can a Harvard organization support
simultaneous instruction fetch
and data access?
\end{block}

\vspace{0.35cm}

\begin{block}{Question 5: Modified Harvard}
How does a typical modified-Harvard processor
combine separate instruction/data paths

\end{block}

% ============================================================

\begin{frame}{Self-Test: Solutions 4--5}

\begin{block}{Solution 4}
Von Neumann uses
a shared instruction/data memory path,
so the two access types can contend.

Harvard provides
separate instruction and data memories/paths,
allowing both accesses
to proceed concurrently.
\end{block}

\vspace{0.3cm}

\begin{block}{Solution 5}
A modified-Harvard processor commonly uses
separate L1 instruction
and data caches near the core
while sharing lower-level caches
and main memory
within one unified address space.
\end{block}

\end{frame}
