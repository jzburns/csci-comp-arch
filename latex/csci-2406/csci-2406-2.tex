\sectiondivider{Section 01}{The Call and Return\\Mechanism}

% --- Slide 4: The Need for Procedures ---
\begin{frame}{The Need for Procedures}
    Procedures (functions, subroutines, methods) are the primary abstraction for software modularity.

    \vspace{0.3em}
    To execute a procedure, the hardware must successfully manage:
    \begin{itemize}
        \item \key{Control Transfer}: Jump to the subroutine's memory address.
        \item \key{State Preservation}: Ensure the caller's data is not destroyed by the callee.
        \item \key{Argument Passing}: Transmit inputs to the subroutine.
        \item \key{Value Return}: Transmit outputs back to the caller.
        \item \key{Return Linkage}: Remember exactly where to resume the original execution.
    \end{itemize}
\end{frame}

% --- Slide 5: Branch and Link (BL) ---
\begin{frame}{Branch and Link (\code{BL})}
    The \code{BL} instruction solves the control transfer and return linkage problems simultaneously.

    \vspace{0.2em}
    \begin{block}{Execution semantics of \code{BL label}}
        \begin{enumerate}
            \item Computes the return address: the address of the instruction immediately following the \code{BL}.
            \item Stores this return address into the \key{Link Register (\code{x30})}.
            \item Overwrites the Program Counter (\code{PC}) with the address of \code{label}.
        \end{enumerate}
    \end{block}

    \vspace{0.2em}
    \key{Why not just use \code{B} (Branch)?}\\
    A standard branch overwrites the \code{PC} but does \textit{not} save the return address. The processor would have no way to find its way back to the caller.
\end{frame}

% --- Slide 6: Return (RET) ---
\begin{frame}{Return (\code{RET})}
    The \code{RET} instruction completes the subroutine lifecycle by transferring control back to the caller.

    \vspace{0.2em}
    \begin{block}{Execution semantics of \code{RET}}
        \begin{itemize}
            \item Reads the memory address currently stored in \code{x30} (the Link Register).
            \item Unconditionally branches to that address (\code{PC} $\leftarrow$ \code{x30}).
        \end{itemize}
    \end{block}

    \vspace{0.2em}
    \begin{alertblock}{The Link Register Vulnerability}
        If a subroutine calls \textit{another} subroutine (a nested call), the inner \code{BL} will overwrite \code{x30}. The original return address is lost forever unless it is backed up to memory before the nested call.
    \end{alertblock}
\end{frame}

\sectiondivider{Section 02}{The Hardware Stack}

% --- Slide 8: The Hardware Stack ---
\begin{frame}{The Hardware Stack}
    To solve the nested call problem and provide space for local variables, architectures utilize a \key{Stack} in Main Memory (RAM).

    \vspace{0.2em}
    \begin{itemize}
        \item \key{Structure}: A Last-In, First-Out (LIFO) memory queue.
        \item \key{Direction}: The AArch64 stack is \textbf{Full Descending}. It grows from high memory addresses down toward lower memory addresses.
        \item \key{Stack Pointer (\code{SP})}: A dedicated architectural register that holds the memory address of the last item pushed onto the stack.
    \end{itemize}

    \vspace{0.3em}
    \textit{Note: Unlike x86, AArch64 does not have dedicated \code{PUSH} and \code{POP} assembly instructions. We construct stack operations manually using load/store instructions.}
\end{frame}

% --- Slide 9: Stack Alignment Constraints ---
\begin{frame}{Stack Pointer (\code{SP}) Alignment Constraints}
    \begin{block}{The 16-Byte Rule}
        In AArch64, the Stack Pointer (\code{SP}) must \textbf{always be 16-byte aligned} when used as a base register for memory access.
    \end{block}

    \vspace{0.3em}
    \begin{itemize}
        \item The memory address held in \code{SP} must end in \hex{0} (i.e., be a multiple of 16).
        \item If you attempt a \code{LDR} or \code{STR} using an unaligned \code{SP}, the processor hardware generates an alignment fault (exception).
        \item Consequence: You must allocate stack space in chunks of at least 16 bytes, even if you only need to save an 8-byte register.
    \end{itemize}
\end{frame}

% --- Slide 10: Pushing and Popping ---
\begin{frame}{Simulating Push and Pop (\code{STP} / \code{LDP})}
    We use \key{pre-indexed} and \key{post-indexed} addressing modes to manipulate the stack efficiently.

    \vspace{0.2em}
    \begin{columns}[T,onlytextwidth]
        \begin{column}{0.48\textwidth}
            \begin{block}{Pushing to the Stack}
                \code{stp x29, x30, [sp, -16]!}
                \begin{enumerate}
                    \item Subtracts 16 from \code{SP} (growing the stack down).
                    \item Stores \code{x29} and \code{x30} into the newly allocated 16-byte slot.
                    \item The \code{!} updates \code{SP} to the new address permanently.
                \end{enumerate}
            \end{block}
        \end{column}
        \begin{column}{0.48\textwidth}
            \begin{block}{Popping from the Stack}
                \code{ldp x29, x30, [sp], 16}
                \begin{enumerate}
                    \item Loads \code{x29} and \code{x30} from the current \code{SP} address.
                    \item Adds 16 to \code{SP} (shrinking the stack up).
                    \item \code{SP} is updated automatically \textit{after} the load completes.
                \end{enumerate}
            \end{block}
        \end{column}
    \end{columns}
\end{frame}

\sectiondivider{Section 03}{The AAPCS64 Convention}

% --- Slide 12: The AAPCS64 Standard ---
\begin{frame}{The AAPCS64 Standard}
    The \key{ARM Architecture Procedure Call Standard} (AAPCS64) is the software contract that compilers (like GCC and Clang) follow. It dictates exactly which registers are used for arguments, returns, and variables.

    \vspace{0.4em}
    \begin{table}[]
        \centering
        \small
        \renewcommand{\arraystretch}{1.4}
        \begin{tabular}{@{} >{\raggedright\arraybackslash}p{2.5cm} >{\raggedright\arraybackslash}p{10cm} @{}}
            \toprule
            \rowcolor{navy}
            \textcolor{white}{\textbf{Registers}} & \textcolor{white}{\textbf{Designated Purpose}} \\
            \midrule
            \rowcolor{lightblue}
            \key{\code{x0}--\code{x7}} & Arguments 1 through 8 (also used to return values in \code{x0}--\code{x1}). \\
            \rowcolor{softgray}
            \key{\code{x8}} & Indirect result location register (struct returns). \\
            \rowcolor{lightblue}
            \key{\code{x9}--\code{x15}} & Temporary registers (Caller-saved / Volatile). \\
            \rowcolor{softgray}
            \key{\code{x19}--\code{x28}} & Callee-saved registers (Non-volatile). \\
            \rowcolor{lightblue}
            \key{\code{x29} (\code{FP})} & Frame Pointer (anchors the local stack frame). \\
            \rowcolor{softgray}
            \key{\code{x30} (\code{LR})} & Link Register (holds the return address). \\
            \bottomrule
        \end{tabular}
    \end{table}
\end{frame}

% --- Slide 13: Caller-Saved vs. Callee-Saved ---
\begin{frame}{Register Volatility: Caller-Saved vs. Callee-Saved}
    \begin{columns}[T,onlytextwidth]
        \begin{column}{0.48\textwidth}
            \begin{block}{Caller-Saved (\code{x0-x18})}
                \begin{itemize}
                    \item These registers are \textbf{volatile}.
                    \item A subroutine is free to overwrite them without backing them up.
                    \item If the caller cares about the data in \code{x0-x18}, the \textit{caller} must push them to the stack before invoking \code{BL}.
                \end{itemize}
            \end{block}
        \end{column}
        \begin{column}{0.48\textwidth}
            \begin{block}{Callee-Saved (\code{x19-x28})}
                \begin{itemize}
                    \item These registers are \textbf{non-volatile}.
                    \item If a subroutine wants to use them, the \textit{callee} must back them up to the stack first, and restore them before calling \code{RET}.
                    \item The caller trusts these will not change across a function call.
                \end{itemize}
            \end{block}
        \end{column}
    \end{columns}
\end{frame}

\sectiondivider{Section 04}{Practical C to Assembly}

% --- Slide 15: C to Assembly Translation ---
\begin{frame}[fragile]{C to Assembly Translation: Procedure Calls}
    \begin{columns}[T,onlytextwidth]
        \begin{column}{0.42\textwidth}
            \begin{block}{C Source Code}
\begin{verbatim}
long sum(long a, long b) {
    return a + b;
}

long main() {
    return sum(5, 10);
}
\end{verbatim}
            \end{block}
            \vspace{0.5em}
            \small
            \textbf{Compiler behavior}:
            \begin{itemize}
                \item Maps \code{a} to \code{x0}, \code{b} to \code{x1}.
                \item Expects return value in \code{x0}.
                \item Must preserve \code{x30} in \code{main} because \code{main} makes a nested call to \code{sum}.
            \end{itemize}
        \end{column}

        \begin{column}{0.55\textwidth}
            \begin{block}{AArch64 Assembly (GCC -O1)}
\begin{verbatim}
sum:
    add     x0, x0, x1
    ret

main:
    // 1. Prologue: Save FP and LR
    stp     x29, x30, [sp, -16]!
    mov     x29, sp

    // 2. Setup Arguments
    mov     x1, 10
    mov     x0, 5

    // 3. Call Function
    bl      sum

    // 4. Epilogue: Restore FP and LR
    ldp     x29, x30, [sp], 16
    ret
\end{verbatim}
            \end{block}
        \end{column}
    \end{columns}
\end{frame}

% --- Slide 16: Deconstructing the C Example ---
\begin{frame}{Deconstructing the Compilation Strategy}
    \begin{itemize}
        \item \key{The Leaf Function (\code{sum})}: Because \code{sum} does not call any other function, it is a "leaf." It does not overwrite \code{x30}, so it does not need to allocate stack space. It simply performs math and returns immediately.
        \item \key{The Nested Function (\code{main})}: \code{main} is called by the OS loader (meaning \code{x30} contains the OS return address). Because \code{main} calls \code{sum}, the \code{bl sum} instruction will destroy the OS return address.
        \item \key{The Solution}: \code{main} pushes \code{x30} (and \code{x29}) to the stack in its \textbf{Prologue}, executes the program, and pops them back in its \textbf{Epilogue} before returning.
    \end{itemize}
\end{frame}

\sectiondivider{Section 05}{Stack Frames}

% --- Slide 18: Stack Frames ---
\begin{frame}{Stack Frames (Activation Records)}
    A \key{Stack Frame} is the block of memory allocated on the stack for a single execution of a subroutine.

    \vspace{0.2em}
    \begin{block}{What goes in a Stack Frame?}
        \begin{itemize}
            \item Saved registers (like \code{x30} LR and \code{x29} FP).
            \item Saved Callee-saved registers (\code{x19-x28}) if the function modifies them.
            \item Local variables (arrays, structs, or variables that do not fit in registers).
            \item Spilled arguments (if a function takes more than 8 parameters, arguments 9+ are passed on the stack).
        \end{itemize}
    \end{block}
\end{frame}

% --- Slide 19: The Frame Pointer (x29) ---
\begin{frame}{The Frame Pointer (\code{x29})}
    As functions push and pop variables, the Stack Pointer (\code{SP}) moves continuously. This makes addressing local variables via \code{[sp, \#offset]} difficult, as the offset changes dynamically.

    \vspace{0.3em}
    \begin{itemize}
        \item \key{The Frame Pointer (\code{x29} / \code{FP})}: Serves as a fixed reference anchor for the current stack frame.
        \item Standard practice immediately after pushing \code{x29}/\code{x30} is to copy the stack pointer: \code{mov x29, sp}.
        \item Compilers map local variables relative to \code{x29} (e.g., \code{[x29, \#16]}). This address remains completely stable regardless of how much additional data is pushed to \code{SP}.
        \item \code{FP} also forms a linked list of frames, allowing debuggers to trace the call stack in the event of a crash.
    \end{itemize}
\end{frame}

% --- Slide 22: Concept Check 1 ---
\begin{frame}{Self-Test: Concept Check 1}
    \key{Question 1: Subroutine Calls}

    You are analyzing AArch64 assembly and notice a subroutine that does \textbf{not} push the Link Register (\code{x30}) to the stack, yet the program executes and returns successfully.
    \vspace{0.4em}

    \key{Why is this possible?}
    \begin{enumerate}[A)]
        \item The subroutine is a "leaf" function that makes no inner \code{BL} calls.
        \item The hardware automatically backs up \code{x30} to the stack.
        \item The compiler used a caller-saved register to store the return address instead.
        \item The code violates AAPCS64 but gets lucky at runtime.
    \end{enumerate}
    \vspace{0.2em}
    \pause
    \begin{block}{Answer: A}
        If a function never executes a \code{BL} instruction, \code{x30} is never overwritten, so it does not need to be backed up to the stack.
    \end{block}
\end{frame}

% --- Slide 23: Concept Check 2 ---
\begin{frame}{Self-Test: Concept Check 2}
    \key{Question 2: Stack Management}

    An AArch64 developer writes the following instruction to back up the \code{x19} register before modifying it:
    \code{str x19, [sp, -8]!}
    \vspace{0.4em}

    \key{What will happen when this code runs on physical hardware?}
    \begin{enumerate}[A)]
        \item \code{x19} is successfully pushed to the stack.
        \item The assembler will convert it to a 16-byte push automatically.
        \item The processor will trigger a hardware alignment fault and crash.
        \item The data is stored, but \code{SP} is not updated.
    \end{enumerate}
    \vspace{0.2em}
    \pause
    \begin{block}{Answer: C}
        The AArch64 Stack Pointer (\code{SP}) must be strictly 16-byte aligned. Subtracting 8 from \code{SP} breaks alignment and causes an immediate hardware exception on memory access.
    \end{block}
\end{frame}
