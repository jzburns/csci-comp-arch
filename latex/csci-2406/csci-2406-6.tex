\begin{frame}{The ELF Memory Layout Paradigm}
\begin{block}{What is ELF?}
ELF (Executable and Linkable Format) is the standard binary file format for executables, object code, and shared libraries in Unix-like systems.
\end{block}
\vspace{0.3em}
\begin{itemize}
\item Defines how code, static data, and linking symbols are organized on disk and loaded into memory.
\item Contains processor-specific flags, such as machine type identification and alignment requirements.
\item When an ELF binary executes, the operating system maps it into virtual memory segments.
\end{itemize}
\end{frame}

\begin{frame}{The Linux Virtual Memory Map}
\begin{columns}[T]
\begin{column}{0.52\textwidth}
\begin{itemize}
\item \textbf{Kernel Space}: Reserved space for kernel code, process tables, and kernel stacks.
\item \textbf{User Stack}: Grows downward; stores local variables and activation frames.
\item \textbf{Shared Libraries}: Mapped memory regions for dynamic libraries.
\item \textbf{Runtime Heap}: Grows upward via dynamic allocation (\code{malloc}).
\item \textbf{BSS / Data / Text}: Uninitialized, initialized, and executable code segments.
\end{itemize}

% ============================================================
% Slide 7
% Slide Header: Load-Store Architecture Principles
% ============================================================
\begin{frame}{Load-Store Architecture Principles}
AArch64 follows a strict RISC load-store design philosophy:
\vspace{0.2em}
\begin{itemize}
\item \key{Separation of Concerns}: Computation instructions (\code{add}, \code{sub}) process register operands exclusively. Memory instructions (\code{ldr}, \code{str}) handle data movement.
\item \key{No In-Memory Arithmetic}: An instruction cannot simultaneously fetch from memory, add, and write back.
\item \key{Simplified Datapath}: Keeps hardware control logic streamlined, highly predictable, and optimized for deep pipelining.
\end{itemize}
\vspace{0.3em}
\begin{block}{C Code Implication}
C statements like \code{a = b + c;} require explicit loading of variables from memory into registers, addition, and a final store instruction.
\end{block}
\end{frame}

% ============================================================
% Slide 8
% Slide Header: Memory Addresses as Register Values
% ============================================================
\begin{frame}{Memory Addresses as Register Values}
Memory locations are targeted using 64-bit virtual addresses held in general-purpose registers:
\vspace{0.3em}
\begin{itemize}
\item The base address of a variable, array, or data structure is loaded into an \code{x} register (e.g., \code{x1}).
\item Load/store instructions treat this register as a pointer referencing the target byte location.
\item Pointer arithmetic can manipulate base addresses dynamically.
\end{itemize}
\vspace{0.4em}
\begin{block}{Pointer Register Rule}
Only 64-bit general-purpose registers (\code{x0}--\code{x30}) can serve as base address pointers in AArch64.
\end{block}
\end{frame}

% ============================================================
% Slide 9
% Slide Header: Load and Store Instructions
% ============================================================
\sectiondivider{Section 03}{Load and Store Instructions}

% ============================================================
% Slide 10
% Slide Header: Loading Data: The ldr Instruction
% ============================================================
\begin{frame}{Loading Data: The \code{ldr} Instruction}
The Load Register (\code{ldr}) instruction copies data from memory into a target register:
\vspace{0.3em}
\begin{itemize}
\item \key{Syntax Format}: \code{ldr destination\_reg, [base\_register]}
\item \key{64-bit Transfer}: \code{ldr x0, [x1]} loads 8 bytes from the address in \code{x1} into \code{x0}.
\item \key{32-bit Transfer}: \code{ldr w0, [x1]} loads 4 bytes into \code{w0}, zero-extending the upper 32 bits of \code{x0}.
\end{itemize}
\vspace{0.4em}
\begin{block}{Data Sizing Suffixes}
Sub-word loads are supported via explicit qualifiers like \code{ldrb} (byte) and \code{ldrh} (halfword), with sign-extended variants (\code{ldrsb}, \code{ldrsh}).
\end{block}
\end{frame}

% ============================================================
% Slide 11
% Slide Header: Storing Data: The str Instruction
% ============================================================
\begin{frame}{Storing Data: The \code{str} Instruction}
The Store Register (\code{str}) instruction copies data from a register into memory:
\vspace{0.3em}
\begin{itemize}
\item \key{Syntax Format}: \code{str source\_reg, [base\_register]}
\item \key{64-bit Transfer}: \code{str x0, [x1]} writes the 8-byte contents of \code{x0} to the memory address held in \code{x1}.
\item \key{32-bit Transfer}: \code{str w0, [x1]} writes the lower 4 bytes of \code{w0} to memory.
\end{itemize}
\vspace{0.4em}
\begin{block}{Sub-Word Stores}
Corresponding store variants \code{strb} (store byte) and \code{strh} (store halfword) allow granular writing of lower register bytes to memory destinations.
\end{block}
\end{frame}

% ============================================================
% Slide 12
% Slide Header: Precision Data Sizing and Sign Extension
% ============================================================
\begin{frame}{Precision Data Sizing and Sign Extension}
AArch64 load instructions allow precise control over data width and extension behavior:
\vspace{0.2em}
\begin{center}
\small
\begin{tabular}{p{3.2cm} p{3.0cm} p{5.4cm}}
\toprule
\textbf{Instruction} &
\textbf{Bytes Loaded} &
\textbf{Extension Behavior} \\
\midrule
\code{ldrb w0, [x1]} &
1 Byte ($8$ bits) &
Zero-extended to 32 bits in \code{w0} \\
\code{ldrsb x0, [x1]} &
1 Byte ($8$ bits) &
Sign-extended to 64 bits in \code{x0} \\
\code{ldrh w0, [x1]} &
2 Bytes ($16$ bits) &
Zero-extended to 32 bits in \code{w0} \\
\code{ldrsh x0, [x1]} &
2 Bytes ($16$ bits) &
Sign-extended to 64 bits in \code{x0} \\
\bottomrule
\end{tabular}
\end{center}
\vspace{0.2em}
\begin{block}{Sign Extension Importance}
When loading signed 8-bit or 16-bit integers into larger registers, using sign-extended variants (\code{ldrsb}/\code{ldrsh}) preserves negative values correctly.
\end{block}
\end{frame}

\sectiondivider{Section 04}{Memory Addressing Modes}

% ============================================================

% Slide Header: Addressing Mode Classification
% ============================================================
\begin{frame}{Addressing Mode Classification}
An addressing mode defines how the CPU calculates the target memory address for a load or store instruction:
\vspace{0.2em}
\begin{itemize}
\item \key{Base Register (Indirect)}: Address is taken directly from the base register.
\item \key{Immediate Offset}: Adds a constant offset to the base register without modifying the base.
\item \key{Register Offset}: Adds a scaling or offset register to the base address.
\item \key{Pre-Indexed}: Applies an offset, updates the base register, and accesses memory.
\item \key{Post-Indexed}: Accesses memory using the base address, then updates the base register.
\end{itemize}
\end{frame}

% ============================================================
% Slide 15
% Slide Header: Base Register (Indirect) Addressing
% ============================================================
\begin{frame}{Base Register (Indirect) Addressing}
\begin{block}{Syntax and Semantics}
\vspace{0.05cm}
\large
\hspace{4.0cm}\code{ldr x0, [x1]}
\normalsize
\vspace{0.05cm}

The memory address is taken strictly from the contents of the base register \code{x1}. The base register remains unchanged after execution.
\end{block}
\vspace{0.3em}
\begin{itemize}
\item \key{Use Case}: Accessing a variable or dereferencing a pointer whose exact address is already loaded in a register.
\item Analogous to pointer dereferencing in C: \code{*ptr}.
\end{itemize}
\end{frame}

% ============================================================
% Slide 16
% Slide Header: Immediate Offset Addressing
% ============================================================
\begin{frame}{Immediate Offset Addressing}
\begin{block}{Syntax and Semantics}
\vspace{0.05cm}
\large
\hspace{4.0cm}\code{ldr x0, [x1, \#16]}
\normalsize
\vspace{0.05cm}

Computes the target address by adding an immediate constant offset (\code{+\#16}) to the base register \code{x1}. The base register \code{x1} is \textbf{not} modified.
\end{block}
\vspace{0.3em}
\begin{itemize}
\item \key{Use Case}: Accessing fields within a structure or fixed offsets in a local stack frame.
\item Immediate range rules depend on transfer size.
\end{itemize}
\end{frame}

% ============================================================
% Slide 17
% Slide Header: Pre-Indexed Addressing Mode
% ============================================================
\begin{frame}{Pre-Indexed Addressing Mode}
\begin{block}{Syntax and Semantics}
\vspace{0.05cm}
\large
\hspace{4.0cm}\code{ldr x0, [x1, \#8]!}
\normalsize
\vspace{0.05cm}

The immediate offset (\code{+\#8}) is added to base register \code{x1}. This new calculated address is used for the memory load, \textbf{and} is written back into \code{x1}.
\end{block}
\vspace{0.3em}
\begin{itemize}
\item Identified by the trailing exclamation mark (\code{!}).
\item \key{Use Case}: Updating a pointer before accessing the next sequential memory item.
\end{itemize}
\end{frame}

% ============================================================
% Slide 18
% Slide Header: Post-Indexed Addressing Mode
% ============================================================
\begin{frame}{Post-Indexed Addressing Mode}
\begin{block}{Syntax and Semantics}
\vspace{0.05cm}
\large
\hspace{4.0cm}\code{ldr x0, [x1], \#8}
\normalsize
\vspace{0.05cm}

Data is loaded from the unmodified address in \code{x1}. After the memory access completes, the offset (\code{+\#8}) is added to \code{x1}, updating the pointer register.
\end{block}
\vspace{0.3em}
\begin{itemize}
\item Identified by placing the offset outside the square brackets.
\item \key{Use Case}: Fetching current array elements and automatically advancing the pointer for the next iteration.
\end{itemize}
\end{frame}

% ============================================================
% Slide 19
% Slide Header: Register Offset and Scaled Addressing
% ============================================================
\begin{frame}{Register Offset and Scaled Addressing}
AArch64 allows an index register to offset the base pointer, optionally scaled by data size:
\vspace{0.3em}
\begin{itemize}
\item \key{Syntax}: \code{ldr x0, [x1, x2]} $\rightarrow$ Address is $\code{x1} + \code{x2}$.
\item \key{Scaled Register Offset}: \code{ldr x0, [x1, x2, lsl \#3]} $\rightarrow$ Address is $\code{x1} + (\code{x2} \times 8)$.
\end{itemize}
\vspace{0.3em}
\begin{block}{Array Indexing Power}
Scaling shifts the index register by the exact byte width of the data item ($2^3 = 8$ bytes for doublewords), mapping C array subscripts directly into hardware addressing.
\end{block}
\end{frame}

% ============================================================
\begin{frame}{Addressing Mode Summary}
\begin{table}[]
\centering
\small
\begin{tabular}{p{2.6cm} p{4.2cm} p{2.4cm} p{2.8cm}}
\toprule

Offset and index quantities can be specified as general-purpose registers, as shown above, or compatible immediate byte constants such as \code{\#8}.
\end{block}
\end{frame}

% ============================================================

% Slide Header: Memory Alignment Rules in AArch64
% ============================================================
\begin{frame}{Memory Alignment Rules in AArch64}
Data alignment dictates how memory addresses map to data sizes:
\vspace{0.2em}
\begin{itemize}
\item \key{Natural Alignment}: An $n$-byte data item should be stored at an address divisible by $n$.
\begin{itemize}
\item Doublewords ($8$ bytes) are naturally aligned at addresses divisible by $8$.
\item Words ($4$ bytes) are naturally aligned at addresses divisible by $4$.
\item Halfwords ($2$ bytes) are naturally aligned at addresses divisible by $2$.
\end{itemize}
\item \key{Performance and Correctness}: Alignment requirements depend on the particular access and system configuration; naturally aligned accesses are generally preferred.
\end{itemize}
\end{frame}

% ============================================================
% Slide 23
% Slide Header: Load and Store Pair Instructions
% ============================================================
\begin{frame}{Load and Store Pair Instructions (\code{ldp} / \code{stp})}
AArch64 provides specialized instructions to transfer \textbf{two registers} with one instruction:
\vspace{0.3em}
\begin{itemize}
\item \key{Load Pair (\code{ldp})}: \code{ldp x0, x1, [x2]} loads two 64-bit registers from consecutive memory locations starting at \code{x2}.
\item \key{Store Pair (\code{stp})}: \code{stp x0, x1, [x2]} stores two 64-bit registers consecutively to memory.
\end{itemize}
\vspace{0.3em}
\begin{block}{Instruction-Count Benefit}
Pair instructions move two register values with one architectural instruction and are especially useful for stack-frame save/restore operations.
\end{block}
\end{frame}

% ============================================================
% Slide 24
% Slide Header: Stack Operations via Pair Transfers
% ============================================================
\begin{frame}{Stack Operations via Pair Transfers}
Stack management relies heavily on pre-index and post-index pair instructions:
\vspace{0.3em}
\begin{block}{Pushing to the Stack (Pre-Index)}
\vspace{0.05cm}
\large
\hspace{3.0cm}\code{stp x29, x30, [sp, \#-16]!}
\normalsize
\vspace{0.05cm}

Decrements stack pointer (\code{sp}) by $16$ bytes, then stores frame pointer (\code{x29}) and link register (\code{x30}).
\end{block}
\vspace{0.2em}
\begin{block}{Popping from the Stack (Post-Index)}
\vspace{0.05cm}
\large
\hspace{4.0cm}\code{ldp x29, x30, [sp], \#16}
\normalsize
\vspace{0.05cm}

Loads registers from current \code{sp}, then increments stack pointer by $16$ bytes, restoring stack balance.
\end{block}
\end{frame}

\begin{frame}{Initializing Base Pointers in C and Assembly}
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{C Pointer Initialization}
\small
\begin{itemize}
\item \code{int array[6] = \{2, 3, 11, 4, 55, 6\};}
\item \code{int *ptr = array; // base pointer}
\item \code{*(ptr += 4) += 10;}
\end{itemize}
\end{block}
\end{column}
\begin{column}{0.48\textwidth}
\begin{block}{AArch64 Base Register Setup}
\small
\begin{itemize}
\item Declare static data arrays in the \code{.data} section.
\item Load the array base address into a pointer register using symbol directives:
\item \code{ldr x0, =array}
\end{itemize}
\end{block}
\end{column}
\end{columns}
\end{frame}

% ============================================================
% Slide 27
% Slide Header: Mapping C Arrays to AArch64 Assembly
% ============================================================
\begin{frame}{Mapping C Arrays to AArch64 Assembly}
Arrays consist of contiguous memory locations holding elements of identical size:
\vspace{0.2em}
\begin{itemize}
\item Let \code{x1} hold the base address of an integer array (\code{int A[]}, where each element is 4 bytes).
\item Accessing element \code{A[i]} requires computing the effective address:
\[
\text{Base} + (\text{Index} \times \text{Element Size})
\]
\item Assembly implementations can use scaled register offsets or explicit pointer arithmetic.
\end{itemize}
\vspace{0.2em}
\begin{block}{Example Array Access}
\code{ldr w0, [x1, x2, lsl \#2]} loads \code{A[i]} into \code{w0}, where \code{x2} holds index \code{i} and the shift multiplies it by $4$.
\end{block}
\end{frame}

% ============================================================
% Slide 28
% Slide Header: Iterating Over Strings
% ============================================================
\begin{frame}{Iterating Over Strings (\code{.asciz})}
Strings in C/C++ are represented as contiguous character arrays terminated by a null byte ($0$):
\vspace{0.3em}
\begin{itemize}
\item Declared using assembler directives such as \code{message: .asciz "Hello World!"}.
\item Accessing individual characters requires byte-level instructions such as \code{ldrb}.
\item Using a post-indexed byte load, \code{ldrb w1, [x0], \#1}, fetches the current character and then advances the pointer.
\end{itemize}
\vspace{0.3em}
\begin{block}{Loop Termination Check}
The loop continues reading until the loaded character equals zero, for example with \code{cmp w1, \#0} followed by \code{b.eq end}.
\end{block}
\end{frame}

\begin{frame}{Topic 6 Comprehensive Summary}
\begin{itemize}
\item \key{ELF Memory Layout}: Programs execute across mapped virtual regions including text, data, BSS, heap, mapped regions, and stack.
\item \key{Load-Store Paradigm}: Memory access uses explicit load/store instructions; arithmetic and logical computation operates on registers.
\item \key{Addressing Modes}: AArch64 supports base, immediate offset, register offset, pre-indexed, and post-indexed addressing forms.
\item \key{Alignment \& Pairs}: Natural alignment is preferred, while \code{ldp} and \code{stp} provide efficient pair transfers.
\item \key{Data Structures}: Scaled offsets, pointers, and byte loads support array and string traversal.
\end{itemize}
\end{frame}

\begin{frame}{Self-Test: Questions 1 \& 2}
\begin{block}{Question 1: ELF Segments}
What is the primary difference between the \code{.text} segment and the \code{.data} segment in an ELF executable?
\end{block}
\vspace{0.4em}
\begin{block}{Question 2: Immediate vs. Indexed Addressing}
What is the primary operational difference between immediate offset addressing (\code{[x1, \#8]}) and pre-indexed addressing (\code{[x1, \#8]!})?
\end{block}
\end{frame}

% ============================================================
% Slide 32
% Slide Header: Self-Test: Solutions 1 & 2
% ============================================================
\begin{frame}{Self-Test: Solutions 1 \& 2}
\begin{block}{Solution 1}
The \code{.text} segment stores the program's executable machine instructions, while the \code{.data} segment stores initialized global and static variables.
\end{block}
\vspace{0.3em}
\begin{block}{Solution 2}
Immediate offset adds the constant to the base register solely to calculate the target address, leaving the base register unchanged. Pre-indexed addressing calculates the address \textbf{and writes the updated address back} into the base register.
\end{block}
\end{frame}

\begin{frame}{Self-Test: Questions 3 \& 4}
\begin{block}{Question 3: Post-Indexed String Traversal}
How does the instruction \code{ldrb w1, [x0], \#1} simplify iterating through a null-terminated string compared with using a separate addition instruction?
\end{block}
\vspace{0.4em}
\begin{block}{Question 4: Memory Alignment}
Why is natural alignment generally preferred for memory accesses?
\end{block}
\end{frame}

% ============================================================
% Slide 34
% Slide Header: Self-Test: Solutions 3 & 4
% ============================================================
\begin{frame}{Self-Test: Solutions 3 \& 4}
\begin{block}{Solution 3}
It loads the byte at the current address in \code{x0} into \code{w1} and then increments \code{x0} by 1 as part of the same architectural instruction, eliminating a separate \code{add x0, x0, \#1}.
\end{block}
\vspace{0.3em}
\begin{block}{Solution 4}
Natural alignment matches the data size to an appropriately aligned address and generally avoids unnecessary access complexity or implementation-dependent penalties.
\end{block}
\end{frame}

\begin{frame}{Self-Test: Questions 5 \& 6}
\begin{block}{Question 5: Pair Transfers on the Stack}
How do \code{stp} and \code{ldp} manage stack pointer updates during function entry and exit?
\end{block}
\vspace{0.4em}
\begin{block}{Question 6: Scaled Register Addressing}
In the instruction \code{ldr x0, [x1, x2, lsl \#3]}, what role does the \code{lsl \#3} modifier play in indexing an array of 64-bit integers?
\end{block}
\end{frame}

% ============================================================
% Slide 36
% Slide Header: Self-Test: Solutions 5 & 6
% ============================================================
\begin{frame}{Self-Test: Solutions 5 \& 6}
\begin{block}{Solution 5}
Using pre-indexed store pair (\code{stp ... [sp, \#-16]!}), the stack pointer is decremented before the registers are stored. Post-indexed load pair (\code{ldp ... [sp], \#16}) restores the registers and then increments the stack pointer.
\end{block}
\vspace{0.3em}
\begin{block}{Solution 6}
The \code{lsl \#3} scales the index in \code{x2} by multiplying it by $2^3 = 8$, the byte size of a 64-bit element, translating an array index into a byte offset.
\end{block}
\end{frame}
