\sectiondivider{Section 01}{Bits, Bytes, Words, and\\Base Conversions}

% --- Slide 4: Why Data Representation Matters ---
\begin{frame}{Why Data Representation Matters}
All machine-level information is stored as fixed-width bit patterns:
\vspace{0.2em}
\begin{itemize}
\item \key{Context Dependent}: The same bit pattern can mean different things under different interpretations (e.g., \hex{FF} can be $255$ unsigned or $-1$ signed).
\item \key{ISA Rules}: Software interpretation determines whether bits represent data items, memory addresses, or machine instructions.
\item \key{Fixed-Width Bounds}: Registers impose strict hardware width limits on numeric ranges.
\item \key{Layout Rules}: Memory organization dictates how multi-byte values are mapped and retrieved.
\end{itemize}
\end{frame}

% --- Slide 5: Bits, Bytes, and Words ---
\begin{frame}{Data Units in Memory and Registers}
\begin{block}{Hierarchical Units of Storage}
\begin{itemize}
\item \key{Bit}: A single binary digit ($0$ or $1$).
\item \key{Byte}: Contains $8$ bits; the foundational unit of addressable memory.
\item \key{Halfword}: Commonly $16$ bits ($2$ bytes).
\item \key{Word}: Commonly $32$ bits ($4$ bytes) in standard architectures.
\item \key{Doubleword}: Commonly $64$ bits ($8$ bytes), native to AArch64 registers (\code{x0}--\code{x30}).
\end{itemize}
\end{block}
\vspace{0.2em}
\begin{block}{Example}
One AArch64 register width = $64$ bits = $8$ bytes.
\end{block}
\end{frame}

% --- Slide 6: Binary Number System ---
\begin{frame}{The Binary Number System (Base 2)}
Binary maps directly to physical dual-state digital hardware:
\vspace{0.2em}
\begin{itemize}
\item Each digit position represents a distinct power of two.
\item \key{LSB (Least Significant Bit)}: The rightmost bit position ($2^0$).
\item \key{MSB (Most Significant Bit)}: The leftmost bit position in a fixed-width container.
\end{itemize}
\vspace{0.3em}
\begin{block}{Positional Evaluation Example}
\[
1011_2
=
(1 \times 8)
+
(0 \times 4)
+
(1 \times 2)
+
(1 \times 1)
=
11_{10}
\]
\end{block}
\end{frame}

% --- Slide 7: Converting Binary and Decimal ---
\begin{frame}{Base Conversion Mechanics}
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{Binary to Decimal}
\begin{itemize}
\item Write power-of-two weights above each bit ($2^0, 2^1, 2^2 \dots$).
\item Disregard positions where the bit is $0$.
\item Sum the weights where the bit is $1$.
\item Example: $01010110_2 = 64 + 16 + 4 + 2 = 86_{10}$.
\end{itemize}
\end{block}
\end{column}
\begin{column}{0.48\textwidth}
\begin{block}{Decimal to Binary}
\begin{itemize}
\item Repeatedly divide the decimal value by $2$.
\item Record each remainder as a binary digit.
\item Read remainders from bottom to top.
\item Pad with leading zeros to match container width.
\item Example: $13_{10} = 1101_2$.
\end{itemize}
\end{block}
\end{column}
\end{columns}
\end{frame}

\sectiondivider{Section 02}{Binary and Hexadecimal Representation}

% --- Slide 9: Hexadecimal Number System ---
\begin{frame}{The Hexadecimal Number System (Base 16)}
Hexadecimal provides a compact, readable shorthand for machine-level data:
\vspace{0.2em}
\begin{itemize}
\item Digits range from $0$ to $9$ and letters $A$ to $F$ (representing values $10$ to $15$).
\item \key{Exact Mapping}: Each single hexadecimal digit maps precisely to $4$ binary bits ($2^4 = 16$).
\item Used universally for memory addresses, instruction opcodes, and register dumps.
\end{itemize}
\vspace{0.3em}
\begin{block}{Example}
\[
\text{0x2A}
=
0010\,1010_2
=
(2 \times 16) + 10
=
42_{10}
\]
\end{block}
\end{frame}

% --- Slide 10: Binary-Hexadecimal Conversion ---
\begin{frame}{Direct Binary-Hexadecimal Conversion}
Converting between binary and hex requires no intermediate decimal math:
\vspace{0.3em}
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{Binary to Hexadecimal}
\begin{itemize}
\item Group binary bits into sets of four starting from the right (LSB).
\item Pad the leftmost group with leading zeros if necessary.
\item Map each 4-bit nibble directly to its hex digit.
\item Example: $1101\,0110_2 = \text{0xD6}$.
\end{itemize}
\end{block}
\end{column}
\begin{column}{0.48\textwidth}
\begin{block}{Hexadecimal to Binary}
\begin{itemize}
\item Take each individual hex character.
\item Expand it into its exact 4-bit binary equivalent.
\item Concatenate the nibbles together.
\item Example: $\text{0x5F} = 0101\,1111_2$.
\end{itemize}
\end{block}
\end{column}
\end{columns}
\end{frame}

% --- Slide 11: AArch64 Registers and Data Widths ---
\begin{frame}{AArch64 Registers and Data Widths}
AArch64 general-purpose registers are 64 bits wide, supporting flexible data sizing:
\vspace{0.2em}
\begin{itemize}
\item A 64-bit register (\code{x0}--\code{x30}) holds $64$ bits of raw data.
\item The exact same bit pattern can be interpreted as signed integers, unsigned integers, pointers, or masks.
\item Memory instructions (\code{ldr}, \code{str}) explicitly specify access sizes such as bytes, halfwords, words, and doublewords.
\end{itemize}
\vspace{0.3em}
\begin{block}{Example Interpretation}
Setting \code{x0 = 0xFFFFFFFFFFFFFFFF} can represent the unsigned integer
$18,446,744,073,709,551,615$ or the signed integer $-1$.
\end{block}
\end{frame}

\sectiondivider{Section 03}{Unsigned and Signed Integer Representations}

% --- Slide 13: Unsigned Integer Representation ---
\begin{frame}{Unsigned Integer Representation}
Unsigned integers represent only non-negative values ($0$ and positive integers):
\vspace{0.2em}
\begin{itemize}
\item Every bit position contributes a strictly positive power-of-two weight.
\item The leftmost bit (MSB) acts as a high-order magnitude bit, not a sign indicator.
\item An $n$-bit unsigned container spans the exact range from $0$ to $2^n - 1$.
\end{itemize}
\vspace{0.3em}
\begin{block}{Unsigned Range Examples}
\begin{itemize}
\item 8-bit unsigned range: $0$ to $2^8 - 1 = 255$.
\item 64-bit unsigned range: $0$ to $2^{64} - 1 \approx 1.84 \times 10^{19}$.
\item Example: $1111\,1111_2 = 255$ in 8 bits.
\end{itemize}
\end{block}
\end{frame}

% --- Slide 14: Unsigned Arithmetic Overflow ---
\begin{frame}{Unsigned Arithmetic and Fixed-Width Limits}
Unsigned operations are evaluated modulo $2^n$ for an $n$-bit container:
\vspace{0.2em}
\begin{itemize}
\item \key{Fixed-Width Bound}: When an unsigned addition exceeds the maximum representable value ($2^n - 1$), the fixed-width register cannot expand.
\item \key{Truncation \& Modular Behavior}: High-order carry bits exceeding the bit width are truncated, leaving the low $n$ bits as the result modulo $2^n$.
\item Processors can record unsigned carry-out conditions in status flags.
\end{itemize}
\vspace{0.3em}
\begin{block}{Classic Overflow Example}
In 8-bit unsigned arithmetic:
\[
255 + 1
=
1111\,1111_2 + 1
=
0000\,0000_2
=
0
\]
with a carry out.
\end{block}
\end{frame}

% --- Slide 15: Signed Integer Representation & Sign-Magnitude Flaws ---
\begin{frame}{Signed Integer Challenges \& Sign-Magnitude Failure}
Signed integers require encoding both positive and negative values:
\vspace{0.2em}
\begin{itemize}
\item \key{Naive Approach (Sign-Magnitude)}: Dedicate the MSB as a sign flag ($0 = \text{positive}, 1 = \text{negative}$).
\item \key{Problems with Sign-Magnitude}:
\begin{itemize}
\item \textbf{Dual Zeros}: Encodes both positive zero ($00000$) and negative zero ($10000$).
\item \textbf{Arithmetic Complication}: Ordinary binary addition cannot simply treat all sign-magnitude bit patterns as fixed-width integers and obtain correct signed arithmetic.
\end{itemize}
\end{itemize}
\vspace{0.2em}
\begin{block}{The Engineering Solution}
Modern general-purpose processors use \key{two's-complement representation} for signed integers.
\end{block}
\end{frame}

\sectiondivider{Section 04}{Two's Complement Representation\\and Arithmetic Behavior}

% --- Slide 17: Two's Complement Solution ---
\begin{frame}{Two's Complement Representation}
\begin{block}{Core Design Objective}
Two's complement allows signed addition and subtraction to use the same fixed-width binary-adder structure used for unsigned arithmetic, while maintaining a single representation for zero.
\end{block}
\vspace{0.3em}
\begin{block}{Algorithm for Negation}
\begin{enumerate}
\item Start with the positive magnitude in binary.
\item \key{Invert every bit} ($0 \rightarrow 1$, $1 \rightarrow 0$).
\item \key{Add 1} to the inverted result.
\end{enumerate}
\end{block}
\vspace{0.2em}
\begin{itemize}
\item Example, $-5$ in 8 bits:
$0000\,0101 \rightarrow 1111\,1010 \rightarrow 1111\,1011$.
\end{itemize}
\end{frame}

% --- Slide 18: Two's Complement Adder Execution ---
\begin{frame}{Two's Complement in Action: $-9 + 6$}
Standard fixed-width binary addition produces the correct two's-complement result:
\vspace{0.2em}
\begin{center}
\begin{tikzpicture}[scale=0.9, every node/.style={font=\small}]

  draw=navy,
  fill=lightblue,
  text=darkgray,
  rounded corners=2pt,
  text width=4.0cm,
  align=center
] (b1) at (0,2.4) {
  \textbf{$-9$ (5-bit Two's Complement)}\\
  \code{10111}
};

\node[
  draw=navy,
  fill=lightblue,
  text=darkgray,
  rounded corners=2pt,
  text width=4.0cm,
  align=center

  \textbf{$+6$ (5-bit Positive)}\\
  \code{00110}
};

\node[

\vspace{-0.1em}
\begin{itemize}
\item Adding \code{10111} ($-9$) and \code{00110} ($+6$) yields \code{11101}, which represents $-3$.
\end{itemize}
\end{frame}

% --- Slide 19: Two's Complement Range ---
\begin{frame}{Two's Complement Numeric Range}
An $n$-bit container under two's-complement encoding spans asymmetric bounds:
\vspace{0.2em}
\begin{itemize}
\item \key{Total Patterns}: $2^n$ unique bit combinations.
\item \key{Signed Range}: $-2^{n-1}$ to $2^{n-1} - 1$.
\item \key{Asymmetry}: There is one more negative value than positive value because zero occupies one bit pattern.
\item The most negative value has only its most significant bit set ($1000\dots0$).
\end{itemize}
\vspace{0.3em}
\begin{block}{8-Bit and 64-Bit Ranges}
\begin{itemize}
\item 8-bit two's-complement range: $-128$ to $+127$.
\item 64-bit two's-complement range: $-9,223,372,036,854,775,808$ to $+9,223,372,036,854,775,807$.
\end{itemize}
\end{block}
\end{frame}

% --- Slide 20: Signed Overflow Detection ---
\begin{frame}{Signed Arithmetic Overflow}
\begin{block}{Definition of Signed Overflow}
Signed overflow occurs when a mathematical signed result lies outside the representable range of the destination width.
\end{block}
\vspace{0.3em}
\begin{itemize}
\item For addition, overflow occurs when two operands with the same sign produce a result with the opposite sign.
\item Hardware can detect overflow from operand and result sign bits or equivalent carry relationships at the most significant bit.
\item In AArch64, flag-setting arithmetic records signed overflow in the \key{V} flag.
\item Example in 8-bit arithmetic:
$127 + 1 = 0111\,1111 + 0000\,0001 = 1000\,0000$.
The bit pattern represents $-128$, so signed overflow occurred.
\end{itemize}
\end{frame}

% --- Slide 21: Interpreting Carry and Overflow Flags ---
\begin{frame}{Do Carry and Overflow Represent Error Conditions?}
\begin{block}{Status Flags vs. Hardware Errors}
The \textbf{C} and \textbf{V} flags are arithmetic indicators, not automatic exceptions.
\end{block}
\vspace{0.3em}
\begin{itemize}
\item \key{Carry Flag (C)}:
for addition, records carry out of the selected width; for subtraction, AArch64 uses it to represent no borrow.
\begin{itemize}
\item Carry may be expected, for example in multiword unsigned arithmetic.
\end{itemize}
\item \key{Overflow Flag (V)}:
indicates that a signed arithmetic result cannot be represented in the selected width.
\begin{itemize}
\item Software may explicitly test the condition, for example with \code{b.vs}.
\end{itemize}
\end{itemize}
\end{frame}

\sectiondivider{Section 05}{Memory Endianness and\\Data Alignment in AArch64}

% --- Slide 23: Memory as a Byte-Addressed Structure ---
\begin{frame}{Memory as a Byte-Addressed Structure}
AArch64 memory is organized as a byte-addressed structure:
\vspace{0.2em}
\begin{itemize}
\item Each memory address identifies one 8-bit byte.
\item Multi-byte values occupy consecutive byte addresses.
\item A multi-byte object's address normally identifies its lowest-addressed byte.
\end{itemize}
\vspace{0.3em}
\begin{block}{Example: 64-Bit Doubleword Layout}
A 64-bit value beginning at address \hex{1000} occupies byte addresses
\hex{1000}, \hex{1001}, \hex{1002}, \hex{1003},
\hex{1004}, \hex{1005}, \hex{1006}, and \hex{1007}.
\end{block}
\end{frame}

% --- Slide 24: Endianness Definition ---
\begin{frame}{Endianness: Ordering Multi-Byte Values}
\begin{block}{Definition}
\key{Endianness} defines the ordering of bytes when a multi-byte value is stored across consecutive memory addresses.
\end{block}
\vspace{0.3em}
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{Big-Endian Ordering}
\begin{itemize}
\item Stores the \key{most significant byte} at the lowest memory address.
\item The remaining bytes follow toward increasing addresses.
\end{itemize}
\end{block}
\end{column}
\begin{column}{0.48\textwidth}
\begin{block}{Little-Endian Ordering}
\begin{itemize}
\item Stores the \key{least significant byte} at the lowest memory address.
\item This is the usual configuration encountered in modern AArch64 systems.
\end{itemize}
\end{block}
\end{column}
\end{columns}
\end{frame}

% --- Slide 25: Endianness in AArch64 ---
\begin{frame}{Little-Endian Layout in AArch64 Practice}
AArch64 implementations commonly operate with little-endian data accesses:
\vspace{0.2em}
\begin{itemize}
\item The numerical value held in a register is conceptually independent of how its bytes are ordered in memory.
\item Loads assemble register values from memory bytes according to the configured byte order.
\item Stores place register-value bytes into memory according to that byte order.
\item Endianness becomes especially visible when examining memory one byte at a time.
\end{itemize}
\vspace{0.3em}
\begin{block}{Concrete Layout Example}
Storing the 64-bit value \hex{1234567890ABCDEF} beginning at address \hex{2000} in little-endian order gives:
\[
\begin{array}{c|cccccccc}
\text{Address} &
\text{\hex{2000}} &
\text{\hex{2001}} &
\text{\hex{2002}} &
\text{\hex{2003}} &
\text{\hex{2004}} &
\text{\hex{2005}} &
\text{\hex{2006}} &
\text{\hex{2007}}
\\
\hline
\text{Byte} &
\text{\hex{EF}} &
\text{\hex{CD}} &
\text{\hex{AB}} &
\text{\hex{90}} &
\text{\hex{78}} &
\text{\hex{56}} &
\text{\hex{34}} &
\text{\hex{12}}
\end{array}
\]
\end{block}
\end{frame}

% --- Slide 26: Data Alignment in AArch64 ---
\begin{frame}{Data Alignment in AArch64}
\begin{block}{Natural Alignment}
An object is naturally aligned when its starting address is a multiple of its size in bytes.
\end{block}
\vspace{0.3em}
\begin{itemize}
\item \key{64-Bit Doubleword}: naturally aligned at addresses divisible by $8$.
\item \key{32-Bit Word}: naturally aligned at addresses divisible by $4$.
\item \key{16-Bit Halfword}: naturally aligned at addresses divisible by $2$.
\item Natural alignment generally simplifies and can improve memory-system access.
\item AArch64 permits many ordinary unaligned data accesses, but behavior and performance can depend on the access type, memory attributes, and implementation.
\end{itemize}
\end{frame}

\sectiondivider{Section 06}{Summary \& Self-Test}

% --- Slide 28: Topic Summary ---
\begin{frame}{Topic 3 Comprehensive Summary}
\begin{itemize}
\item \key{Fixed-Width Representation}: Information is stored as bit patterns whose meaning depends on interpretation and context.
\item \key{Base Conversions}: Binary (base 2) and hexadecimal (base 16) provide useful notations for machine-level values.
\item \key{Unsigned Integers}: Represent non-negative values from $0$ through $2^n - 1$ in an $n$-bit width.
\item \key{Two's Complement}: Provides the standard fixed-width representation for signed integers and supports signed arithmetic using ordinary binary-adder structures.
\item \key{Endianness \& Alignment}: Byte ordering determines how multi-byte values map to memory, while alignment describes the relationship between object size and starting address.
\end{itemize}
\end{frame}

% --- Slide 29: Self-Test: Questions 1 & 2 ---
\begin{frame}{Self-Test: Questions 1 \& 2}
\begin{block}{Question 1: Bits, Words, and Bases}
What is the relationship between bits, bytes, words, and 64-bit AArch64 registers?
Why is hexadecimal usually easier to read than binary when inspecting machine-level values?
\end{block}
\vspace{0.4em}
\begin{block}{Question 2: Unsigned Arithmetic Limits}
What range of values can be represented by an unsigned $n$-bit integer?
What happens when an 8-bit unsigned value of $255$ has $1$ added to it?
\end{block}
\end{frame}

% --- Slide 30: Self-Test: Solutions 1 & 2 ---
\begin{frame}{Self-Test: Solutions 1 \& 2}
\begin{block}{Solution 1}
A bit is one binary digit; a byte contains 8 bits; in AArch64 terminology a word is 32 bits, while the \code{x} general-purpose register view is 64 bits.
Hexadecimal is compact because each hex digit maps directly to four binary bits.
\end{block}
\vspace{0.3em}
\begin{block}{Solution 2}
An unsigned $n$-bit container represents values from $0$ to $2^n - 1$.
For 8 bits, $255 + 1$ produces a low 8-bit result of $0$ modulo $256$, with carry out.
\end{block}
\end{frame}

\begin{frame}{Self-Test: Questions 3 \& 4}
\begin{block}{Question 3: Two's Complement Negation}
How do you form the two's-complement negative of a positive binary number?
What signed range is representable in a 32-bit two's-complement integer?
\end{block}
\vspace{0.4em}
\begin{block}{Question 4: Signed vs. Unsigned Interpretation}
How can the same 32-bit pattern represent different numerical values when interpreted as signed versus unsigned?
\end{block}
\end{frame}

% --- Slide 32: Self-Test: Solutions 3 & 4 ---
\begin{frame}{Self-Test: Solutions 3 \& 4}
\begin{block}{Solution 3}
To form the two's-complement negative of a representable positive value, invert every bit and add $1$.
A 32-bit two's-complement integer spans
$-2^{31}$ through $2^{31}-1$.
\end{block}
\vspace{0.3em}
\begin{block}{Solution 4}
Unsigned interpretation assigns non-negative powers-of-two weights to all bit positions.
Two's-complement interpretation assigns the most significant bit a negative positional weight.
Thus \hex{FFFFFFFF} represents $4,294,967,295$ unsigned but $-1$ signed.
\end{block}
\end{frame}

% --- Slide 33: Self-Test: Questions 5 & 6 ---
\begin{frame}{Self-Test: Questions 5 \& 6}
\begin{block}{Question 5: Endianness in Memory}
What is the difference between little-endian and big-endian byte ordering?
Which ordering is most commonly encountered in AArch64 systems?
\end{block}
\vspace{0.4em}
\begin{block}{Question 6: Data Alignment}
What does natural alignment mean, and why can alignment matter to a memory system?
\end{block}
\end{frame}

% --- Slide 34: Self-Test: Solutions 5 & 6 ---
\begin{frame}{Self-Test: Solutions 5 \& 6}
\begin{block}{Solution 5}
Little-endian places the least significant byte at the lowest address.
Big-endian places the most significant byte at the lowest address.
Modern AArch64 systems are commonly configured for little-endian data accesses.
\end{block}
\vspace{0.3em}
\begin{block}{Solution 6}
Natural alignment means that an object's starting address is a multiple of its size in bytes.
Aligned accesses are generally easier for memory hardware to handle efficiently, while unaligned-access behavior and cost can depend on the access and implementation.
\end{block}
\end{frame}
