\begin{frame}{What Is Architectural State?}

\begin{itemize}\setlength{\itemsep}{5pt}
  \item \key{Definition:} The complete set of software-visible hardware storage locations required to represent a program's execution at any discrete point in time.
  \item If execution is interrupted (context switch, interrupt, exception), saving and restoring this exact state allows program resumption without alteration of behavior.
  \item \key{Core Components in AArch64:}
  \begin{itemize}\setlength{\itemsep}{2.5pt}
    \item General-Purpose Registers (\bits{x0}--\bits{x30}).
    \item Program Counter (\bits{pc}) and Stack Pointer (\bits{sp}).
    \item Current Program Status Register / Condition Flags (\bits{pstate} / NZCV).
    \item System control and configuration registers (e.g., $\text{TTBR0\_EL1}$, $\text{SCTLR\_EL1}$ for exception/virtualization management).
    \item Byte-addressed memory contents.
  \end{itemize}
\end{itemize}

\vfill
\begin{block}{State Checkpointing}
Operating systems actively rely on the strict definition of architectural state to successfully suspend and resume millions of threads per second without computational corruption.
\end{block}

\end{frame}

% ============================================================
% Slide 4 (FIXED: Reduced padding and flattened nested lists)

\begin{frame}{Architectural vs.\ Microarchitectural State}
\vfill
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{Architectural State (Visible Contract)}
\begin{itemize}\setlength{\itemsep}{3pt}
  \item Defined strictly by the ISA specification.
  \item Software directly reads/writes this state.
  \item \key{Examples:} Registers \bits{x0}--\bits{x30}, \bits{pc}, architectural memory, NZCV flags.
\end{itemize}
\end{block}
\end{column}

\begin{column}{0.48\textwidth}
\begin{block}{Microarchitectural State (Hidden)}
\begin{itemize}\setlength{\itemsep}{3pt}
  \item Internal hardware implementation details.
  \item Invisible to software correctness.
  \item \key{Examples:} Pipeline latches, L1/L2 caches, Branch Target Buffers, rename tables.
\end{itemize}
\end{block}
\end{column}
\end{columns}

\vfill
\begin{block}{The Execution Boundary}
Hardware may wildly execute instructions out of order across hidden microarchitectural buffers, but it \key{must} commit all final mathematical results sequentially to the visible architectural state.
\end{block}
\end{frame}

% ============================================================
% Slide 5 (FIXED: Flattened sub-bullets into a single line)

\begin{frame}{The AArch64 Execution State}

\begin{itemize}\setlength{\itemsep}{6pt}
  \item \key{AArch64:} Pure 64-bit execution state introduced in ARMv8-A.
  \item \key{Flat 64-bit Virtual Addressing:} Registers hold 64-bit pointers (architectural address space up to $2^{64}$ bytes). Fixed 4-byte instruction width remains permanently aligned to 4-byte memory boundaries.
  \item \key{Clean-Slate RISC Design:} Eliminates legacy A32 quirks by removing universal conditional execution, removing \code{ldm}/\code{stm} loops, and decoupling the Program Counter (\bits{pc}) entirely from the general register file.
\end{itemize}

\vfill
\begin{block}{The Legacy-Free Advantage}
By abandoning strict backwards compatibility with 32-bit ARM inside the AArch64 execution mode, engineers freed up massive decode logic and instruction-encoding space.
\end{block}

\end{frame}

\begin{frame}{General-Purpose Registers: \texttt{x0}--\texttt{x30}}

\begin{itemize}\setlength{\itemsep}{4pt}
  \item AArch64 provides \key{31 general-purpose registers} (\bits{x0}--\bits{x30}), each exactly \key{64 bits wide} ($8\text{ bytes}$).
  \item \key{Orthogonal Design:} Any of these registers can serve interchangeably as a source, destination, or base address pointer without restriction.
  \item \key{Simplified ISA:} Eliminates the highly dedicated register constraints (e.g., implicit counter registers) found in legacy architectures like x86.
\end{itemize}

\vfill
\centering
\begin{tikzpicture}[scale=0.9, every node/.style={transform shape}]
  \draw[fill=lightblue, draw=navy, thick] (0,0) rectangle (9.0,0.5);
  \node at (4.5, 0.25) {\small\textbf{\texttt{x0}--\texttt{x30} (64-Bit Full Doubleword Register)}};
  \node[anchor=south, font=\tiny\bfseries] at (0.3, 0.5) {Bit 63};
  \node[anchor=south, font=\tiny\bfseries] at (8.7, 0.5) {Bit 0};
\end{tikzpicture}

\vfill
\begin{block}{Why Exactly 31 Registers?}
RISC instructions allocate precisely 5 bits to encode a register operand ($2^5 = 32$). AArch64 dedicates 31 of these slots to general storage and reserves the 32nd slot for a hardwired Zero Register / Stack Pointer alias.
\end{block}

\end{frame}

% ============================================================
% Slide 8
% ============================================================

\begin{frame}{32-Bit Register Views: \texttt{w0}--\texttt{w30}}

\begin{itemize}\setlength{\itemsep}{4pt}
  \item Every 64-bit \bits{x} register has a corresponding 32-bit view denoted as \bits{w0} through \bits{w30}.
  \item \bits{wN} represents the \key{lower 32 bits (bits 31:0)} of the physical register \bits{xN}.
  \item This aliasing enables efficient execution of native 32-bit integer operations (like C \code{int} variables) without requiring separate hardware register files.
\end{itemize}

\vfill
\centering
\begin{tikzpicture}[scale=0.85, every node/.style={transform shape}]
  \draw[fill=softgray, draw=navy, dashed] (0,0) rectangle (6.0,0.65);
  \node at (3.0, 0.325) {\footnotesize\textit{Upper 32 bits [63:32] (Zeroed on write)}};
  \draw[fill=lightblue, draw=navy, thick] (6.0,0) rectangle (11.5,0.65);
  \node at (8.75, 0.325) {\small\textbf{\texttt{wN} (Lower 32 bits [31:0])}};
  \node[anchor=south, font=\tiny\bfseries] at (0.2, 0.65) {Bit 63};
  \node[anchor=south, font=\tiny\bfseries] at (6.0, 0.65) {Bit 32};
  \node[anchor=south, font=\tiny\bfseries] at (11.3, 0.65) {Bit 0};
  \draw[thick, decoration={brace, mirror, raise=4pt}, decorate] (0,0) -- (11.5,0) node[midway, below=6pt, font=\small\bfseries] {\texttt{xN} Full 64-Bit Register};
\end{tikzpicture}

\vfill
\begin{block}{Zero-Extension Safety Rule}
Writing any data to a 32-bit \bits{w} register \key{automatically zero-extends} the value, completely wiping out the upper 32 bits of the corresponding \bits{x} register to clear out potential garbage data.
\end{block}
\end{frame}

% ============================================================
% Slide 9
% ============================================================

\begin{frame}{The Zero Register: \texttt{xzr} and \texttt{wzr}}

\begin{itemize}\setlength{\itemsep}{4pt}
  \item Encoded as register number 31 within most standard ALU instruction contexts.
  \item \key{Read Behavior:} Always returns the constant value \bits{0} (64-bit \bits{0} for \bits{xzr}, 32-bit \bits{0} for \bits{wzr}).
  \item \key{Write Behavior:} Silently discards any value written to it (serving as a digital bit-bucket).
  \item \key{Architectural Benefit:} Eliminates the need to design dedicated zero-loading instructions or comparison formats, vastly simplifying the ISA.
\end{itemize}

\vfill
\begin{block}{Common Idioms Using the Zero Register}
\small
\begin{tabular}{lll}
\toprule
\textbf{Assembly Instruction} & \textbf{Equivalent Operation} & \textbf{Purpose} \\
\midrule
\code{mov x0, xzr}            & $x_0 \leftarrow 0$            & Clear register $x_0$ to zero \\
\code{subs xzr, x1, x2}       & Evaluate $x_1 - x_2 \to \text{flags}$ & Compare $x_1$ and $x_2$ (alias: \code{cmp x1, x2}) \\
\code{str xzr, [x1]}          & $\text{Mem}[x_1] \leftarrow 0$ & Zero out a 64-bit memory word \\
\bottomrule
\end{tabular}
\end{block}
\end{frame}

% ============================================================

\begin{frame}{Special-Purpose Registers: \texttt{sp}, \texttt{pc}, \texttt{lr}}
\vfill
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{Stack Pointer (\texttt{sp})}
\begin{itemize}\setlength{\itemsep}{3pt}
  \item Dedicated register holding current stack top address.
  \item Must strictly maintain \key{16-byte alignment} when accessing memory in the ABI.
  \item Arithmetic on \bits{sp} is restricted exclusively to stack allocations/deallocations.
\end{itemize}
\end{block}
\end{column}

\begin{column}{0.48\textwidth}
\begin{block}{Program Counter (\texttt{pc})}
\begin{itemize}\setlength{\itemsep}{3pt}
  \item Holds memory address of executing instruction.
  \item \key{Cannot} be read or written directly as a data register (no $\code{mov x0, pc}$).
  \item Accessed indirectly via PC-relative addressing (\code{adr}, \code{adrp}).
  \item Modified via branch and call instructions.
\end{itemize}
\end{block}
\end{column}
\end{columns}

\vfill
\begin{block}{Link Register (\texttt{x30} / \texttt{lr})}
Holds the direct return address generated by subroutine branch-with-link instructions (\code{bl}, \code{blr}). A function returning execution merely writes this value back into the \bits{pc}.
\end{block}
\end{frame}

% ============================================================
% Slide 11
% ============================================================

\begin{frame}{The Calling Convention: Caller- vs.\ Callee-Saved}
\vfill
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{Caller-Saved Registers (\texttt{x0}--\texttt{x17})}
\begin{itemize}\setlength{\itemsep}{3pt}
  \item Primarily used for temporary scratch computations and argument passing.
  \item The caller \key{must} save them to the stack before making a subroutine call if their values are needed later.
  \item The called function (callee) is completely free to overwrite them without restoring.
\end{itemize}
\end{block}
\end{column}

\begin{column}{0.48\textwidth}
\begin{block}{Callee-Saved Registers (\texttt{x19}--\texttt{x28})}
\begin{itemize}\setlength{\itemsep}{3pt}
  \item Safely holds long-lived variables across multiple function calls.
  \item If a called function modifies any of these, it \key{must save the original value to the stack} and successfully restore it before returning.
  \item Guarantees protection of caller state.
\end{itemize}
\end{block}
\end{column}
\end{columns}

\vfill
\begin{block}{The Efficiency Trade-off}
Balancing caller- and callee-saved registers across the ABI deliberately minimizes unnecessary memory traffic and stack spilling during deeply nested software logic.
\end{block}
\end{frame}

\begin{frame}{Process State: \texttt{pstate} and Condition Flags}

\begin{itemize}\setlength{\itemsep}{4pt}
  \item The processor maintains an internal process state register (\bits{pstate}). The upper 4 bits evaluate the \key{NZCV Arithmetic Condition Flags}:
\end{itemize}

\vfill
\begin{center}
\footnotesize
\setlength{\tabcolsep}{6pt}
\begin{tabular}{cll}
\toprule
\textbf{Flag} & \textbf{Name} & \textbf{Condition Under Which Flag Is Set to 1} \\
\midrule
\key{N} & \textbf{Negative} & Result bit 63 (or bit 31) is 1 (negative signed value) \\

\begin{block}{Selective Flag Updates}
Standard ALU instructions (\code{add}, \code{sub}) do \key{not} modify flags. Only instructions with an ``\code{s}'' suffix (\code{adds}, \code{subs}) or comparison instructions (\code{cmp}) update NZCV natively.
\end{block}
\end{frame}

  \item Memory is physically organized as a contiguous sequence of \key{8-bit bytes}.
  \item Every individual byte is assigned a unique 64-bit architectural address.
  \item Data operands span multiple consecutive byte addresses scaling by standard powers of two:
\end{itemize}

\begin{block}{64-Bit Pointer Limitations}
While AArch64 uses 64-bit pointers, current physical silicon and page table designs typically cap valid virtual address space addressing to 48 or 52 bits to save translation overhead.
\end{block}

\end{frame}

\begin{frame}{Memory Alignment Rules}
\vspace{-1em} 
\begin{itemize}\setlength{\itemsep}{4pt}
  \item An access to an $n$-byte operand is \key{naturally aligned} if its memory address is an exact mathematical multiple of $n$: $\text{Address} \pmod n = 0$.
  \item \key{Alignment Requirements:}
  \begin{itemize}\setlength{\itemsep}{2pt}
    \item 32-bit Word access: Address must be a multiple of 4 ($\text{Address} \pmod 4 = 0$).
    \item 64-bit Doubleword access: Address must be a multiple of 8 ($\text{Address} \pmod 8 = 0$).
    \item Instruction fetch: Address must always be a strict multiple of 4.
  \end{itemize}
\end{itemize}

\begin{block}{Alignment Penalties}
Unaligned memory accesses can cross cache-line boundaries, requiring multiple memory transactions and severely degrading bandwidth. Strict environments will throw a hardware fault on unaligned access.
\end{block}
\end{frame}

\begin{frame}{Addressing Modes: Base with Immediate Offset}
\vfill
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{Mechanism ($\text{EA} = x_n + \text{offset}$)}
\begin{itemize}\setlength{\itemsep}{3pt}
  \item Instruction: \code{ldr xt, [xn, \#offset]}
  \item Accesses memory physically at $x_n + \text{offset}$.
  \item \key{No side effects:} Base register $x_n$ remains completely unchanged post-execution.
\end{itemize}
\end{block}
\end{column}

\begin{column}{0.48\textwidth}
\begin{block}{Code Examples}
\small
\begin{tabular}{ll}
\code{ldr x1, [x0]}      & \text{\scriptsize Load $[x_0]$} \\
\code{ldr x2, [x0, \#8]}  & \text{\scriptsize Load $[x_0 + 8]$} \\
\code{str x2, [x0, \#16]} & \text{\scriptsize Store $[x_0 + 16]$} \\
\end{tabular}
\end{block}
\end{column}
\end{columns}

\vfill
\begin{block}{Hardware Offset Range}
Standard immediate offsets are structured as unsigned 12-bit scaled values. For 64-bit doublewords, the hardware scales this value up by 8, yielding a maximum effective offset of $+32760$ bytes.
\end{block}
\end{frame}

\begin{frame}{Advanced Addressing: Pre- and Post-Indexed}
\vfill
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{Pre-Indexed (Update Before Access)}
$$\code{ldr xt, [xn, \#imm]!}$$
\begin{enumerate}\setlength{\itemsep}{2pt}
  \item Update base: $x_n \leftarrow x_n + \text{imm}$.
  \item Access memory at updated address: $x_t \leftarrow \text{Mem}[x_n]$.
\end{enumerate}
\vspace{0.1cm}
Note the exclamation mark (\code{!}) syntax.
\end{block}
\end{column}

\begin{column}{0.48\textwidth}
\begin{block}{Post-Indexed (Update After Access)}
$$\code{ldr xt, [xn], \#imm}$$
\begin{enumerate}\setlength{\itemsep}{2pt}
  \item Access memory at current address: $x_t \leftarrow \text{Mem}[x_n]$.
  \item Update base: $x_n \leftarrow x_n + \text{imm}$.
\end{enumerate}
\vspace{0.1cm}
Base update happens \emph{after} the load.
\end{block}
\end{column}
\end{columns}

\vfill
\begin{block}{Efficiency Impact}
Pointer tracking naturally embeds into memory instructions, thereby eliminating standalone \code{add} overhead when rapidly traversing structural arrays or popping execution stack elements.
\end{block}
\end{frame}

\begin{frame}[fragile]{Loading and Storing Pairs (\texttt{ldp} and \texttt{stp})}

\begin{itemize}\setlength{\itemsep}{6pt}
  \item \key{Core Purpose:} Transfer two completely adjacent 64-bit registers in a single instruction pipeline.
  \item \key{Primary Use Case (Stack Management):}
  \begin{itemize}\setlength{\itemsep}{3pt}
    \item Combines two discrete register movements into one atomic 128-bit memory operation.
    \item Efficiently saves and restores critical function linkage (Frame Pointer $x_{29}$ and Link Register $x_{30}$) securely during active function calls.
  \end{itemize}
  \item \key{Performance Impact:} Issues a unified 128-bit memory bus transaction, fundamentally doubling data transfer throughput compared to split single operations.
\end{itemize}

\vfill
\begin{block}{Stack Frame Construction Example}
\begin{verbatim}
// Push FP (x29) and LR (x30) to stack, pre-decrementing SP by 16 bytes
stp x29, x30, [sp, #-16]! 
\end{verbatim}
\end{block}

\end{frame}

\begin{frame}{Control Flow: Unconditional Branches}

\begin{itemize}\setlength{\itemsep}{4pt}
  \item Control flow instructions structurally redirect program execution by coercing the Program Counter (\bits{pc}).
\end{itemize}

\vfill
\begin{center}
\small
\renewcommand{\arraystretch}{1.2}
\setlength{\tabcolsep}{6pt}
\begin{tabular}{lll}
\toprule
\textbf{Instruction} & \textbf{Name / Syntax} & \textbf{Operational Behavior} \\
\midrule

\bottomrule
\end{tabular}

\begin{block}{PC-Relative Addressing}
Direct branch offsets natively encode as signed binary displacements relative to the current \bits{pc}. This structure mathematically guarantees compiled code executes perfectly completely irrespective of loaded memory position.
\end{block}
\end{frame}

\begin{block}{High-Level C Loop}

\end{block}

\begin{frame}{Conditional Select Instructions: Eliminating Branches}

\begin{itemize}\setlength{\itemsep}{4pt}
  \item Branch instructions natively introduce deep pipeline branch misprediction risks.
  \item AArch64 deliberately mitigates pipeline flushes by deploying \key{conditional select instructions} that strictly choose between loaded operands without branching:
\end{itemize}

\vfill
\begin{center}
\small
\renewcommand{\arraystretch}{1.1}
\setlength{\tabcolsep}{6pt}
\begin{tabular}{lll}
\toprule
\textbf{Instruction} & \textbf{Semantic Operation} & \textbf{C Ternary Equivalent} \\
\midrule
\code{csel  xd, xn, xm, cond} & $x_d \leftarrow \text{cond} \mathbin{?} x_n : x_m$ & \code{d = cond ? n : m;} \\
\code{cinc  xd, xn, cond}       & $x_d \leftarrow \text{cond} \mathbin{?} (x_n + 1) : x_n$ & \code{d = n + (cond ? 1 : 0);} \\

\end{center}

\vfill
\begin{block}{Example: Finding Maximum of Two Values ($\max(x_1, x_2)$)}
\small
\begin{tabular}{lll}
\code{cmp  x1, x2}            & \text{\scriptsize // Compare x1 and x2} \\
\code{csel x0, x1, x2, gt}    & \text{\scriptsize // If x1 > x2, x0 = x1; else x0 = x2 (0 branch penalties!)} \\
\end{tabular}
\end{block}
\end{frame}

\begin{frame}{Topic 3: Comprehensive Summary}

\vfill
\begin{itemize}\setlength{\itemsep}{7pt}
  \item \key{Architectural State:} Precise hardware-software contract fundamentally defined by general registers (\bits{x0}--\bits{x30}), flags (NZCV), stack pointer (\bits{sp}), program counter (\bits{pc}), and byte-addressed memory allocations.
  \item \key{Register Structure:} 31 orthogonal 64-bit registers (\bits{x0}--\bits{x30}) structurally alias 32-bit blocks (\bits{w0}--\bits{w30}); writing to a \bits{w} register safely and strictly clears the upper 32 bits natively.
  \item \key{ABI Rules:} \bits{x0}--\bits{x7} handle execution arguments and returns (caller-saved); \bits{x19}--\bits{x28} securely hold local variables across calls (callee-saved).
  \item \key{Load/Store Operations:} Arithmetic executes exclusively in registers; memory interactions operate strictly via \code{ldr}/\code{str} offset, indexed, or unified paired (\code{ldp}/\code{stp}) modes.
  \item \key{Control Flow:} Branching explicitly evaluates logic via NZCV flags updated dynamically by \code{adds}/\code{subs}/\code{cmp}; utilizing conditional select (\code{csel}) mathematically eliminates branch penalty cycles.
\end{itemize}
\vfill

\end{frame}
