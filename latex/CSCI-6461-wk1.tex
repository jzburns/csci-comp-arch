\begin{frame}{What Computer Architecture Studies}

\begin{itemize}

\item Computer architecture is not just ``parts of a computer.''
It studies the \key{interface between software behavior and
hardware implementation}.

\item The central question is:
\key{what must the machine promise to software, and how can
hardware deliver that promise efficiently?}

\item Architecture includes instruction sets, processor organization,
memory systems, and performance trade-offs.

\item A correct machine is not automatically a good machine;
architecture also asks whether it is fast, efficient, scalable,
and practical.

\end{itemize}

\begin{block}{Course Focus}
We will use ARM AArch64 as the concrete RISC architecture,
but Week 1 builds the representation and performance
foundations first.
\end{block}

\end{frame}

% Slide 3

\begin{frame}{The Core Abstraction Problem}

\begin{columns}[T,onlytextwidth]

\column{0.52\textwidth}

\begin{itemize}

\item Programmers want to write algorithms,
not manipulate voltage levels.

\item Hardware only stores and transforms bit patterns.

\item Abstraction layers make this gap manageable.

\item Each layer hides detail, but hidden detail
can still affect performance.

\end{itemize}

\column{0.42\textwidth}

\begin{block}{Important tension}

Abstraction makes systems usable.

Architecture explains when abstraction leaks:
performance, memory layout, integer overflow,
and instruction costs.

\end{block}

\end{columns}

\end{frame}

\begin{frame}{A Small Example Across the Layers}

\begin{block}{High-level intent}
\texttt{c = a + b;}
\end{block}

\begin{columns}[T,onlytextwidth]

\column{0.48\textwidth}

\begin{itemize}

\item If \texttt{a} and \texttt{b} are already in registers,
a compiler may choose an addition instruction.

\item In AArch64, this could be conceptually written as

\[
\bits{ADD X0, X1, X2}
\]

\item The instruction means:
\key{X0 gets X1 + X2}.

\end{itemize}

\column{0.48\textwidth}

\begin{itemize}

\item The assembler encodes the instruction into 32 bits.

\item Hardware decodes fields for operation
and register numbers.

\item The ALU performs the addition
and writes the result.

\end{itemize}

\end{columns}

\end{frame}

\begin{frame}{ISA vs. Microarchitecture}

\begin{columns}[T,onlytextwidth]

\column{0.48\textwidth}

\begin{block}{ISA: what software sees}

\begin{itemize}
\item Instructions
\item Registers
\item Addressing behavior
\item Architectural state
\item Defined results
\end{itemize}

\end{block}

\column{0.48\textwidth}

\begin{block}{Microarchitecture: how hardware does it}

\begin{itemize}
\item Datapath
\item Control logic
\item Pipeline stages
\item Caches
\item Execution units
\end{itemize}

\end{block}

\end{columns}

\vspace{0.5em}

\key{Key idea:}
Two processors may run the same AArch64 program correctly
but have very different performance.

\end{frame}

\begin{frame}{The Stored-Program Model}

\begin{itemize}

\item Instructions and data are both stored
in memory as bit patterns.

\item A program counter identifies the next
instruction to fetch.

\item The processor repeatedly performs
fetch, decode, execute, and state update.

\item Branches and calls modify the normal
next-instruction sequence.

\item This model is simple, but it is the conceptual
base for pipelines and caches.

\end{itemize}

\begin{block}{Why this matters later}

If instructions live in memory, then memory speed affects
not only data access but also instruction delivery.

\end{block}

\end{frame}

% ============================================================
% Slide 8
% ============================================================

\begin{frame}{Core Hardware Components}

\begin{columns}[T,onlytextwidth]

\column{0.55\textwidth}

\begin{itemize}

\item \key{CPU:} executes instructions.

\item \key{Registers:} hold nearby operands and results.

\item \key{Main memory:} holds active programs and data.

\item \key{Storage:} keeps persistent data.

\item \key{I/O:} connects the machine
to the outside world.

\end{itemize}

\column{0.40\textwidth}

\begin{block}{Architectural consequence}

The processor is fast, memory is slower,
and storage is much slower.

Performance depends heavily on movement
across this hierarchy.

\end{block}

\end{columns}

\end{frame}

\begin{frame}{Why Binary Is Enough}

\begin{itemize}

\item Digital circuits reliably distinguish two voltage ranges,
represented as 0 and 1.

\item A single bit carries little information;
groups of bits carry many possibilities.

\item With \(n\) bits, there are \(2^n\) distinct patterns.

\item Those patterns can represent numbers, characters,
instructions, addresses, or control fields.

\item The hardware does not know the ``meaning''
of a pattern by itself.

\end{itemize}

\begin{block}{Core warning}
Bits are representation. Meaning comes from interpretation.
\end{block}

\end{frame}

% ============================================================
% Slide 10
% ============================================================

\begin{frame}{Unsigned Binary: Place Value}

\begin{center}

\begin{tabular}{c|cccccc}
Bit position & 5 & 4 & 3 & 2 & 1 & 0 \\
\midrule
Weight & 32 & 16 & 8 & 4 & 2 & 1 \\
Bits & 1 & 0 & 1 & 1 & 0 & 1
\end{tabular}

\end{center}

\vspace{0.6em}

\begin{itemize}

\item Binary is positional just like decimal,
but the weights are powers of two.

\item A 1 contributes its weight;
a 0 contributes nothing.

\item \bits{101101} therefore represents

\[
32+8+4+1=45
\]

\item With fixed-width hardware,
the number of available positions is limited.

\end{itemize}

\end{frame}

% ============================================================
% Slide 11
% ============================================================

\begin{frame}{Unsigned Range and Fixed Width}

\begin{itemize}

\item An \(n\)-bit unsigned value has
\(2^n\) possible patterns.

\item The smallest value is 0.

\item The largest value is

\[
2^n-1
\]

\item Four unsigned bits represent 0 through 15.

\item Eight unsigned bits represent 0 through 255.

\item Fixed width is not a formatting detail;
it determines what values are representable.

\end{itemize}

\begin{block}{Architecture connection}

Register widths, immediate fields, and address fields
all impose representational limits.

\end{block}

\end{frame}

% Slide 12
% ============================================================

\begin{frame}{Converting Decimal to Binary}

\begin{block}{Example: convert 45 to binary}

\[
45 = 32 + 8 + 4 + 1
\]

\end{block}

\begin{center}

\begin{tabular}{c|cccccc}
Weight & 32 & 16 & 8 & 4 & 2 & 1 \\
\midrule
Use it? & 1 & 0 & 1 & 1 & 0 & 1
\end{tabular}

\end{center}

\vspace{0.5em}

\begin{itemize}

\item Select the powers of two that sum
to the decimal value.

\item Write 1 where a weight is used
and 0 where it is not.

\item Therefore

\[
45_{10}=101101_2
\]

\end{itemize}

\end{frame}

\begin{block}{Result}

110101_2 = 53_{10}
\]
\end{block}

\begin{frame}{Why Hexadecimal Exists}

\begin{itemize}

\item Long binary strings are difficult for humans to read.

\item Hexadecimal uses 16 symbols:

\[
0,1,\ldots,9,A,B,C,D,E,F
\]

\item One hexadecimal digit represents exactly four bits.

\item Two hexadecimal digits represent one byte.

\item Hexadecimal therefore compresses binary
without hiding the underlying bit boundaries.

\item Addresses and instruction encodings
are commonly written in hexadecimal.

\end{itemize}

\end{frame}

0011\;1101_2 = \hex{3D}

\end{block}

\begin{frame}{The Signed-Integer Problem}

\begin{itemize}

\item Unsigned binary uses all available patterns
for zero and positive values.

\item Real programs also require negative integers.

\item We therefore need a convention that assigns
some bit patterns to negative values.

\item A good representation should make
arithmetic hardware simple.

\item It should also provide predictable
fixed-width behavior.

\item Modern processors overwhelmingly use
\key{two's-complement representation}.

\end{itemize}

\end{frame}

% ============================================================
% Slide 17
% ============================================================

\begin{frame}{Why Not Sign-Magnitude?}

\begin{columns}[T,onlytextwidth]

\column{0.48\textwidth}

\begin{itemize}

\item A simple idea is to reserve one bit for the sign.

\item The remaining bits store the magnitude.

\item This is easy for humans to understand.

\item But it creates both \(+0\) and \(-0\).

\end{itemize}

\column{0.48\textwidth}

\begin{block}{Hardware problem}

Addition becomes conditional:
the arithmetic hardware must consider signs
and magnitudes separately.

\end{block}

\begin{itemize}

\item This complicates datapath design.

\item Two's complement avoids much of this complexity.

\end{itemize}

\end{columns}

\end{frame}

% ============================================================
% Slide 18
% ============================================================

\begin{frame}{Two's-Complement Range}

\begin{itemize}

\item In \(n\) bits, two's complement still has
\(2^n\) total patterns.

\item The lower half of the number line is negative.

\item The upper half includes zero and positive values.

\item The range is

\[
-2^{n-1}
\quad \text{through} \quad
2^{n-1}-1
\]

\item Eight bits represent

\[
-128 \quad \text{through} \quad +127
\]

\item The range is asymmetric because zero
uses one nonnegative pattern.

\end{itemize}

\end{frame}

% ============================================================
% Slide 19
% ============================================================

\begin{frame}{Creating a Negative Value}

\begin{block}{Rule for forming \(-x\) in two's complement}

Write \(+x\) in the required width,
invert all bits, then add 1.

\end{block}

\begin{center}

\begin{tabular}{rl}
\(+5\) in 8 bits: & \bits{00000101} \\[0.25em]
Invert bits: & \bits{11111010} \\[0.25em]
Add 1: & \bits{11111011}
\end{tabular}

\end{center}

\begin{itemize}

\item Therefore \bits{11111011} represents
\(-5\) in 8-bit two's complement.

\item The width is part of the representation;
do not drop leading bits casually.

\end{itemize}

\end{frame}

% ============================================================
% Slide 20
% ============================================================

\begin{frame}{Interpreting a Negative Pattern}

\begin{block}{
Example: interpret \bits{11110110}
as an 8-bit signed integer
}

\begin{center}

\begin{tabular}{rl}
Original: & \bits{11110110} \\[0.25em]
Invert: & \bits{00001001} \\[0.25em]
Add 1: & \bits{00001010} = 10 \\[0.25em]
Result: & \(-10\)
\end{tabular}

\end{center}

\end{block}

\begin{itemize}

\item A leading 1 signals a negative value
in two's complement.

\item The invert-and-add-one procedure
finds the magnitude.

\end{itemize}

\end{frame}

% ============================================================
% Slide 21
% ============================================================

\begin{frame}{Same Bits, Different Interpretation}

\begin{center}

\begin{tabular}{ccc}
\toprule
Bit pattern & Interpretation & Value \\
\midrule
\bits{11111111} & Unsigned 8-bit & 255 \\
\bits{11111111} & Signed 8-bit two's complement & -1 \\
\bits{11111111} & Byte of raw data & Depends on format \\
\bottomrule
\end{tabular}

\end{center}

\begin{itemize}

\item The bits did not change;
only the interpretation changed.

\item Low-level bugs often come from
using the wrong interpretation.

\item Architecture forces us to track
width and signedness explicitly.

\end{itemize}

\end{frame}

\begin{frame}{Binary Addition and Subtraction}

\begin{columns}[T,onlytextwidth]

\column{0.46\textwidth}

\begin{block}{Addition}

\[
0101_2 + 0011_2 = 1000_2
\]

\end{block}

\begin{itemize}

\item Binary addition uses carries
just like decimal addition.

\end{itemize}

\column{0.50\textwidth}

\begin{block}{Subtraction}

\[
A-B = A+(-B)
\]

\end{block}

\begin{itemize}

\item Two's complement lets the same adder
support subtraction.

\item This is a representation choice
with hardware consequences.

\end{itemize}

\end{columns}

\end{frame}

% ============================================================
% Slide 23
% ============================================================

\begin{frame}{Carry vs. Signed Overflow}

\begin{itemize}

\item Carry-out matters for unsigned arithmetic.

\item Signed overflow is different:
it means the signed result is outside
the representable range.

\item In 4-bit signed arithmetic,
the maximum positive value is \(+7\).

\item \bits{0111} represents \(+7\)
and \bits{0011} represents \(+3\).

\item

\[
\bits{0111}+\bits{0011}=\bits{1010}
\]

but \(+10\) cannot fit in four signed bits.

\item The negative-looking result signals
signed overflow, not a valid answer of \(-6\).

\end{itemize}

\end{frame}

% ============================================================
% Slide 24
% ============================================================

\begin{frame}{Sign Extension and Truncation}

\begin{itemize}

\item Sign extension widens a signed value
without changing its mathematical value.

\item It repeats the original most significant bit
into the new high-order bits.

\item Eight-bit \(-5\) is

\[
\bits{11111011}
\]

\item Sixteen-bit \(-5\) is

\[
\bits{11111111 11111011}
\]

\item Truncation does the opposite:
it discards high-order bits.

\item Truncation can destroy information
and change the value completely.

\end{itemize}

\end{frame}

% ============================================================
% Slide 25
% ============================================================

\begin{frame}{Representation Mistakes That Matter}

\begin{itemize}

\item Treating signed data as unsigned
can turn \(-1\) into a large positive value.

\item Forgetting width can make a conversion
appear correct but mean the wrong thing.

\item Ignoring overflow can produce
plausible-looking but incorrect results.

\item Misreading hexadecimal can hide
the bit fields inside an instruction or address.

\item Confusing mathematical integers
with fixed-width machine integers causes subtle bugs.

\item These are not just programming mistakes;
they are architecture-level interpretation mistakes.

\end{itemize}

\end{frame}

% ============================================================
% Slide 26
% ============================================================

\begin{frame}{What Does CPU Performance Mean?}

\begin{itemize}

\item For the same workload,
less execution time means higher performance.

\item Elapsed time may include I/O,
operating-system activity, and waiting.

\item CPU time focuses on processor time
spent executing the program.

\item Clock rate is visible and marketable,
but incomplete.

\item A faster clock can be offset by more instructions
or more cycles per instruction.

\item Architecture uses equations so performance
comparisons do not rely on slogans.

\end{itemize}

\end{frame}

% ============================================================
% Slide 27
% ============================================================

\begin{frame}{Latency vs. Throughput}

\begin{itemize}

\item \key{Latency} is the time for one task to complete.

\item \key{Throughput} is the amount of work completed
per unit time.

\item A processor improvement may reduce latency,
increase throughput, or both.

\item Pipelining often improves throughput more directly
than the latency of one instruction.

\item Users often care about latency;
servers often care heavily about throughput.

\item Distinguishing these terms prevents confusion
when evaluating architectural techniques.

\end{itemize}

\end{frame}

% ============================================================
% Slide 28
% ============================================================

\begin{frame}{Clock Rate and Cycle Time}

\begin{itemize}

\item Clock rate is the number of cycles per second.

\item Cycle time is the duration of one cycle.

\item They are reciprocals:

\[
\text{Cycle Time}
=
\frac{1}{\text{Clock Rate}}
\]

\item A 2 GHz processor has a 0.5 ns cycle time.

\item A 3 GHz processor has a shorter cycle time,
but may not finish a program sooner.

\item Program time also depends on
instruction count and CPI.

\end{itemize}

\end{frame}

% ============================================================
% Slide 29
% ============================================================

\begin{frame}{Instruction Count}

\begin{itemize}

\item Instruction count is the number of
\key{dynamic machine instructions} executed.

\item It is not just the number of lines in a program.

\item Loops can execute the same instruction many times.

\item Instruction count depends on the algorithm,
compiler, ISA, and input data.

\item A program compiled for two different ISAs
may execute different numbers of instructions.

\item Reducing instruction count helps only if CPI
and clock rate do not worsen enough to cancel the gain.

\end{itemize}

\end{frame}

% ============================================================
% Slide 30
% ============================================================

\begin{frame}{Cycles Per Instruction (CPI)}

\begin{itemize}

\item CPI is the average number of clock cycles
per executed instruction.

\item A CPI of 1 does not mean every instruction
takes exactly one cycle.

\item It is an average across the dynamic
instruction stream.

\item Memory stalls, pipeline hazards,
and branch behavior can increase CPI.

\item Better microarchitecture often tries
to reduce CPI without changing the ISA.

\item CPI is where implementation details often
reappear despite software abstraction.

\end{itemize}

\end{frame}

% ============================================================
% Slide 31
% ============================================================

\begin{frame}{The Iron Law of Processor Performance}

\begin{block}{The Iron Law}

\[
\boxed{
\text{CPU Time}
=
\text{Instruction Count}
\times
\text{CPI}
\times
\text{Clock Cycle Time}
}
\]

\[
\boxed{
\text{CPU Time}
=
\frac{
\text{Instruction Count}
\times
\text{CPI}
}{
\text{Clock Rate}
}
}
\]

\end{block}

\begin{itemize}

\item Instruction count connects to software,
compiler, and ISA.

\item CPI connects to microarchitecture
and memory behavior.

\item Clock cycle time connects to circuit timing
and design complexity.

\end{itemize}

\end{frame}

\begin{frame}{Iron Law Worked Example}

\begin{block}{Processor A}

\[
IC=1.0\times10^9,
\qquad
CPI=2.0,
\qquad
Clock=2.0\;GHz
\]

\[
Time
=
\frac{
1.0\times10^9 \times 2.0
}{
2.0\times10^9
}
=
1.0\;s
\]

\end{block}

\begin{block}{Processor B}

\[
IC=1.2\times10^9,
\qquad
CPI=1.2,
\qquad
Clock=2.4\;GHz
\]

\[
Time
=
\frac{
1.2\times10^9 \times 1.2
}{

\begin{frame}{Why GHz Comparisons Fail}

\begin{itemize}

\item Processor B in the example executes
more instructions than Processor A.

\item It still wins because its CPI and clock rate
more than compensate.

\item A higher clock can be defeated by poor CPI.

\item A lower instruction count can be defeated
by slower cycles.

\item A design that improves one term
may worsen another term.

\item The Iron Law forces the full trade-off
to be made explicit.

\end{itemize}

\end{frame}

\begin{frame}{Speedup}

\begin{block}{Definition}

\[
\boxed{
\text{Speedup}
=
\frac{
\text{Old Execution Time}
}{
\text{New Execution Time}
}
}
\]

\end{block}

\begin{itemize}

\item If time falls from 10 seconds to 5 seconds,
speedup is \(2\times\).

\item If time falls from 10 seconds to 8 seconds,
speedup is \(1.25\times\).

\item Speedup greater than 1 means improvement.

\item Speedup below 1 means slowdown.

\item Always specify the workload
and the baseline system.

\end{itemize}

\end{frame}
